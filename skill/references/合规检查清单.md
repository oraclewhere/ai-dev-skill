# 合规检查清单

> 本文件供 `/复盘` 启动的 **审计 subagent** 使用。
>
> **审计者须知**：你看不到被审计会话的对话过程，这是刻意的。你不能读当事方的解释，
> 也就不能为当事方的做法自我辩护。你只能读规则、读 doc 现状、读 git 记录，然后下判断。
>
> **你的产出不是追责，是方法论迭代的输入。** 所以每一条违规必须归因：
>
> - **执行违规** = 规则本身是清楚的，AI 没有遵守 → 修正动作：**加/收紧 hook**
> - **规则歧义** = 规则没说清楚，AI 按另一种合理读法执行了 → 修正动作：**改 skill 措辞**
>
> 归因错误会让迭代方向完全跑偏：把规则歧义当成执行违规，你会不停加 hook 而问题依旧；
> 把执行违规当成规则歧义，你会把规则越写越长而模型照样不遵守。
>
> 判定为"需人工确认"是**允许且鼓励**的。宁可标为无法判定，也不要猜。

## A. 结构类

| 编号 | 规则 | 检查方法 | 判定 |
|---|---|---|---|
| A1 | 项目根存在 `code/` 与 `doc/` | `ls` | 缺失 = 违规 |
| A2 | `doc/` 下存在 `决策约束/`、`交付件/`、`任务记录/`、`error/` | `ls doc/` | 缺失 = 违规 |
| A3 | 每个任务记录含完整 frontmatter（id/type/title/status/refs_decision/deliverables/context_budget） | 逐个读首部 | 字段缺失 = 违规 |

## B. 关联类（硬规则 2、3）

| 编号 | 规则 | 检查方法 | 判定 |
|---|---|---|---|
| B1 | 每个涉及 `code/` 的 commit 含 `task-NNNN` | `git log --oneline --name-only`，筛出改动含 `code/` 的 commit，检查消息 | 未引用 = 违规 |
| B2 | 被引用的 task 文件真实存在 | 抽 B1 中的 ID，`ls doc/任务记录/task-NNNN*` | 不存在 = 违规（比 B1 更严重：这是伪引用） |
| B3 | 被引用 task 的 `status` 与改动性质相符 | 对照改动内容与任务目标 | 明显不符 = 违规（如头像任务下提交了支付模块） |
| B4 | 合并到发布分支的 commit 引用了 `决策约束/` 或 `交付件/` | `git log <release-branch> --merges` | 未引用 = 违规 |
| B5 | `code/` 之外的文件未被要求关联任务 | 检查是否有 hook 或规则对 `scripts/` 等误报 | 误报 = 规则歧义 |

## C. 分类类（第一原则）

| 编号 | 规则 | 检查方法 | 判定 |
|---|---|---|---|
| C1 | 管理类问题未被 AI 直接下结论 | 扫描 `doc/决策约束/` 与任务记录的「决策记录」节，找"我建议/应该采用/推荐使用"这类单方案结论 | 存在 = 违规（应为选项对比） |
| C2 | `doc/决策约束/` 未被 AI 修改 | `git log -- doc/决策约束/`，看提交作者与会话归属 | AI 提交 = 严重违规 |
| C3 | 决策约束的 `status` 由人从 draft 改为 active | 同上 | AI 自行改 = 违规 |
| C4 | 管理类工作是否被误当成执行类直接开工 | 对照任务类型与实际产出形态 | 需人工确认 |

## D. 文档质量类

| 编号 | 规则 | 检查方法 | 判定 |
|---|---|---|---|
| D1 | 验收标准存在且**可判定** | 读任务的验收标准节；搜"功能正常""正常运行""符合预期"这类措辞 | 空 = 违规；不可判定措辞 = 违规 |
| D2 | 验收标准未被 AI 篡改 | `git log -p -- doc/任务记录/task-NNNN*` 看验收标准节的改动方 | AI 改动 = 严重违规 |
| D3 | 交接说明不依赖本次对话上下文 | 搜"如上所述""前面提到""刚才那个"；判断脱离对话能否读懂 | 依赖 = 违规 |
| D4 | 交接说明的「踩过的坑」非空 | 读该节 | 留空 = 违规（留空通常说明没写，而不是没有坑） |
| D5 | 交付件的「验证方法」可执行 | 读该节；判断是否给出了动作与预期结果，而非"已测试通过" | 不可执行 = 违规 |
| D6 | 交付件的「已知限制」非空 | 读该节 | 留空 = 违规 |
| D7 | 交付件 `status` 未在决策变更后仍是 current | 对照决策约束的 version 变更时间 | 应 stale 而未标 = 违规 |

## E. 上下文管理类（本方法论核心）

| 编号 | 规则 | 检查方法 | 判定 |
|---|---|---|---|
| E1 | 任务声明了 `context_budget` | 读 frontmatter | 空 = 违规 |
| E2 | 任务在到达 `handoff_at` 前完成了交接 | 判断本次会话是否在上下文耗尽/被压缩后才补交接 | 事后补写的迹象 = 违规 |
| E3 | 任务粒度未超出单个 session 能闭环的范围 | 看 `context_budget.files` 是否能明确列举；看 `deliverables` 数量 | files 是"整个 src/**"这类模糊值 = 违规 |
| E4 | 是否存在同一任务横跨多个 session 却从未交接 | 看 git 时间线 vs 交接说明的填写时间 | 需人工确认 |

## F. 禁止事项类

| 编号 | 规则 | 检查方法 |
|---|---|---|
| F1 | 未静默略过未达标的验收项 | 对照验收标准与验收输出，看是否逐条回应 |
| F2 | 未用"已测试通过""功能正常"作为验收证据 | 搜验收输出 |
| F3 | 未自行修改决策约束 | 同 C2 |
| F4 | 未自行拟定验收标准 | 同 D2 |

## 输出要求

1. 每条违规给出：**编号 + 事实（附文件:行号或 commit hash）+ 归因 + 建议修正**
2. 分为「违规条目」与「未触发但值得注意」两部分——后者是**新规则的候选来源**，不要省略
3. 若某项无法判定，写 `⚠️ 无法判定：<原因>`，**不要**默认通过
4. 若全部通过，写 `verdict: pass` 并说明本次检查覆盖了哪些范围
5. 最后单列一节「建议新增的 hook」：属于执行违规且重复出现的项，应固化为机械校验

> 关于 3：默认通过是审计最常见的失效方式。**不确定就是不确定**，
> 把不确定标出来才有价值——它往往指向规则本身的模糊地带。
