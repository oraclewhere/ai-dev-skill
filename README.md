# ai-dev-flow

把一个 AI 开发方法论，变成可以被机器执行的流程。

> **大模型的输出是不可预测的，但通过流程管理，我们可以让它的输出保持在一个可控的需求区间内。**

本仓库是这套方法论的工程实现。它不是文档模板集合，而是「**skill（流程）+ hook（强制）+ doc 结构（交付件）**」三件套。

> **刚拿到这个仓库？先读 [INTRO.md](INTRO.md)。**
> 那份是中英双语的完整介绍，包含设计取舍与自测说明，并且**附了方法论原文**；
> 下面这份 README 只讲怎么装、怎么用。

---

## 方法论 → 实现的映射

| 方法论主张 | 实现载体 | 说明 |
|---|---|---|
| 概率性输出要靠流程收束，不能靠提示词消除 | `hooks/` | 凡是能机械校验的规则一律下沉到 hook，不指望模型自觉 |
| 核心管理类「完全质疑」 | `SKILL.md` 第一原则 + `doc/决策约束/` 只读 | 管理类工作 AI 只产出选项对比，不产出结论 |
| 工程执行类「有限怀疑」 | 任务记录的「验收标准」节 | 不审过程，就必须审标准；标准由人定且在执行前存在 |
| 上下文即核心资源 | `context_budget` 字段 + 状态栏 | 工作量单位从人/天变成"能否一个 session 闭环" |
| Session = 高离职率的员工 | `handoff_at` + `/交接` | 文档先行是默认工作方式，不是离职前的临时整理 |
| code-doc 交付件 | `code/` + `doc/{决策约束,交付件,任务记录,error}` | commit 必须关联任务记录，merge 必须关联决策或交付件 |
| 验证 → 完善方法论 | `doc/error/` + `/复盘` | 违规报告归因到「执行违规」或「规则歧义」，两者修正动作不同 |

## 安装

**拆开装**——因为两者的副作用性质相反：

- **skill 装用户级**：它无副作用，你不调用它什么都不做。装全局零风险，而且方法论迭代时改一处全生效。
- **hook 装项目级**：它会拦你，必须只在明确启用规范的项目里生效。

```bash
# 1. 装 skill（用户级，全局可用）
./bin/install.sh skill

# 2. 在某个项目里启用规范（项目级）
./bin/install.sh project /path/to/your-project
```

第 2 步会生成 `code/`、`scripts/`、`doc/` 四目录、`CLAUDE.md`、`.claude/settings.json` 与
`.claude/hooks/`。**已有文件默认跳过不覆盖**，加 `--force` 才覆盖。

依赖：`python3` 或 `jq` 之一（hook 用它解析输入 JSON），以及 `git`。
**注意**：很多机器没有 `jq`。只依赖 jq 的写法会让所有校验静默失效——
规则在纸上存在、在运行时不存在，这是本方法论最不能接受的一种失败，所以改成了 python3 优先、jq 回退。

装完后需要在 Claude Code 里**接受该目录的工作区信任对话框**，否则 hook 不会运行
（`claude -p` 模式例外，它不检查信任）。

**命令名由目录名决定**，不是 frontmatter 里的 `name`——所以安装目标必须叫 `ai-dev-flow/`，
`name` 只影响列表里显示的标签。

> 若日后要把这个 skill 传到 claude.ai（云端 session / Skills API / `package_skill.py` 打包），
> 先删掉 frontmatter 里的 `argument-hint`：它是 Claude Code 的扩展，不在 Agent Skills 规范内，
> 上传时会直接报错（规范只允许 `name`/`description`/`license`/`compatibility`/`metadata`/`allowed-tools`）。
> 本地 `~/.claude/skills/` 用则无影响。

## 使用

```bash
/ai-dev-flow 启动 <需求描述>    # 分类路由：建任务记录，或吐决策待办
/ai-dev-flow 预算               # 把需求切成"一个 session 能闭环"的粒度
/ai-dev-flow 状态               # 一屏看现状
/ai-dev-flow 交接               # 生成交接说明，写回任务记录
/ai-dev-flow 验收               # 逐条对照验收标准
/ai-dev-flow 复盘               # 全新上下文的 subagent 审计合规性
/ai-dev-flow 变更 <变更内容>     # 需求变更传播：升版本 + 标记 stale + 重验清单
```

## 设计决策记录

以下是搭建过程中做过的取舍，写下来是因为半年后会忘记当初排除了什么。

**1. 为什么「对话记录」被合并成「任务记录」？**
原文说对话记录"非强制"，但又说每次提交"必须关联对话记录"——非强制的东西无法作为强制的锚点。
合并后一个任务 = 一个文件，同时充当工单和对话记录，commit 只需写 `task-NNNN`，可校验、可追溯、不臃肿。
原始 transcript 仍可归档作溯源用，但不参与强制校验。

**2. 为什么豁免由「目录路径」决定，而不是由 AI 判断？**
`scripts/` 等 `code/` 之外的文件自动豁免，不需要任何记录。判定条件是"文件在哪个目录"，
机器一查就知。若改成"由 AI 判断这算不算脚本"，等于把"我该不该被监管"的判断权交给被监管者——
模型会倾向于用约束最少的路径解释自己的任务，规则会在短期内退化成不存在。

**3. 为什么审计必须用全新上下文的 subagent？**
同一会话自查合规性，等于让带着注意力漂移的上下文批判自己，模型几乎总会认为自己做得对。
审计者只读规则、doc、git 记录，看不到对话过程，因此无法为当事方自我辩护。
这是"完全质疑"在流程内部的复刻：审计权不交给当事方。

**4. 为什么违规要归因成两类？**
「执行违规」（规则清楚，AI 没遵守）→ 加 hook；「规则歧义」（规则没说清）→ 改措辞。
不区分这两类，迭代会一直改错东西：要么不停加 hook 而问题依旧，要么把规则越写越长而模型照样不遵守。

**5. 为什么流程不由 session 触发？**
触发点是 `commit` / `merge`。聊天、讨论计划、看代码不产生 commit，规范全程静默。
唯一挂在 session 上的是 SessionStart 注入，且仅在存在未结任务时才输出。

**6. 为什么"压缩前强制写交接文档"没有做？**
最初的设计是 `PreCompact` hook 在上下文压缩前逼模型产出交接文档。查证官方文档后放弃了：
`PreCompact` **只能阻断压缩**，无法注入指令、无法引导摘要，`systemMessage` 会被丢弃。
而阻断压缩有真实风险——若压缩是为恢复"上下文超限"错误而触发的，阻断会让当前请求直接失败。

改成三条腿：
- `Stop` hook 在会话结束前催办交接（**这是唯一能让模型真的写出文档的机制**，因为它让会话多跑一轮）
- `PreCompact` 只把机器可读的状态快照落盘（这是它真正做得到的事，且不阻断）
- `SessionStart(source=compact)` 在压缩后把快照重新注入

**7. 为什么交接催办每 session 只触发一次？**
一个每轮都拦的 hook 会训练用户去关掉它——被关掉的规则等于不存在。
所以触发条件必须是客观事实（有 code/ 提交 + 交接说明为空 + 本 session 未催办过），
而不是"感觉差不多该交接了"。

## 自测

```bash
./bin/selftest.sh      # 32 项，覆盖五个 hook 的正常与边界路径
```

**为什么这个套件是必需品而不是锦上添花**：这套东西的立论是"用机械校验替代模型自觉"。
如果校验本身有 bug，结果不是"没效果"，而是**"看起来有效果"**——它不会被人发现。
自测套件搭起来的第一轮就抓出四个真实 bug，其中一个是：

> `section_empty` 的返回值写反了。它在"交接说明已经写好"的时候催办、在"没写"的时候放行。
> 也就是说，它只在你做对的时候打扰你。上线后大概率的表现是"用户觉得这功能很烦然后关掉它"，
> 而真正的问题（交接根本没写）一次都没被拦到。

这个例子本身就是方法论的注脚：**一个会静默通过的校验，比没有校验更危险。**

## 目录

```
skill/                       → 安装到 ~/.claude/skills/ai-dev-flow/
  SKILL.md                   流程主体
  references/                合规检查清单（审计 subagent 读这个）
  assets/templates/          五类文档模板
project/                     → 安装到 <项目>/.claude/
  CLAUDE.md.template         常驻不变量（员工手册）
  hooks/
    _lib.sh                  共享库：JSON 读写、文档解析、依赖探测
    check-commit.sh          硬规则 2：提交必须关联任务记录
    check-merge.sh           硬规则 3：合并必须关联交付件
    inject-context.sh        文档先行：新 session 一进来就知道现状
    stop-handoff.sh          交接催办（每 session 一次）
    precompact-snapshot.sh   压缩前落盘
    statusline.sh            上下文仪表盘
  settings.json              项目级配置（hook）
bin/
  install.sh                 两处安装入口
  selftest.sh                回归测试
```

安装后的 skill 目录是**自包含**的：模板、hook、安装脚本都随 skill 一起走，
所以 `/ai-dev-flow 初始化` 在只装了 skill 的机器上也能用。
