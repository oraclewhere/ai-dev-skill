# 管理 AI 开发 —— 流程规范

## 第 0 步：确认这个项目启用了本规范

**除了 `初始化` 之外的所有子命令，先确认项目里有 `doc/任务记录/` 和 `.claude/hooks/check-commit.sh`。**
没有这两样，说明这个项目没有启用本规范——**直接告诉用户，然后停下**，不要建目录、不要建任务记录、
不要开始走流程。只有用户明确要求 `初始化` 时才生成结构。

> 为什么要在这里再查一遍，而不是信任 `description` 里的自动触发条件：
> 上游过滤是尽力而为的，不保证。这和 hook 里 `if` 字段要 fail-open、脚本必须自己重新检查是同一个道理——
> **约束的第一道闸门不能是唯一一道。** 没有这一查，做法就是在任何仓库里都能把 `doc/` 结构铺开，
> 而那是用户明确反对过的（他只是想改个 bug，不该被追问验收标准）。

## 这套东西在做什么

> **大模型的输出是不可预测的，但通过流程管理，我们可以让它的输出保持在一个可控的需求区间内。**

大模型是概率系统，幻觉、注意力漂移、指令不遵从不是 bug，是概率性输出的必然伴生现象。
消除它不可能，但**在交付节点上捕获并修正它**是可行的。

这套规范用三个机制实现这件事：

| 机制 | 载体 | 作用 |
|---|---|---|
| **不变量** | 项目 `CLAUDE.md` | 常驻上下文，新 session 一进来就知道规矩（= 员工手册） |
| **流程** | 本 skill | 可调用的标准动作（= SOP） |
| **强制** | 项目 `.claude/hooks/` | 不依赖模型自觉的机械校验（= 制度执行者） |

关键立场：**「必须」这两个字不能交给模型自己记。** 指望概率性输出去遵守纪律，就是本方法论要
解决的那个问题本身。凡是能机械校验的规则，一律下沉到 hook；hook 管不了的，才写在文档里靠流程约束。

## 第一原则：先分类，再动手

接到任何请求，**第一步永远是判定它属于哪一类**。分类错了，后面全错。

### 核心管理类 → 态度：完全质疑

**特征**：需要有人对整个项目担责、需要基于全局上下文做取舍。
需求对接 / 需求分解 / 整体架构与技术栈 / 原型与交互决策 / 上下文预算切分 / 最终验收。

**AI 的输出形态不是结论，是可审视的材料。** 具体说：

- ✅ 输出「选项 A / B / C 对比 + 各自代价 + 影响范围 + 待决问题清单」
- ❌ 输出「我建议采用 A」（这已经是在替人做决策了）
- ✅ 把材料写进 `doc/决策约束/` 草稿，`status: draft`，等人确认后由**人**改成 `active`
- ❌ 自己把 `status` 改成 `active`

理由：决策的核心不在于输出是否正确，而在于是否基于全局上下文做出、以及是否有人能为后果负责。
AI 在这两点上都不具备能力。**当你发现自己即将说出"我认为应该……"时，停下来，把它改写成一张对比表。**

### 工程执行类 → 态度：有限怀疑

**特征**：需求明确、边界清晰、有可判定的输出件。
UI 实现 / API 文档 / 测试用例编写 / 模块拆分落地 / 编码与单测 / 联调 / 代码评审 / 缺陷修复 / 部署。

**不审查执行细节，只审查交付件是否满足验收标准。** 这是"有限怀疑"的全部含义：
信任过程，但不信任结果会自动等于预期——因为每一次输出都可能带着微小偏移，
不加审视会在上下游传递中堆积。

**因此有一个不可妥协的前提：验收标准必须在执行前存在，且由人写或人批准。**
不审过程就必须审标准，否则"有限怀疑"会退化成"完全不怀疑"。

## 硬规则

1. 项目根目录必须包含 `code/` 与 `doc/`。`doc/` 下含 `决策约束/`、`交付件/`、`任务记录/`、`error/`。
2. **每一次向 `code/` 的提交，必须关联到一个存在的任务记录 ID**（commit message 中含 `task-NNNN`）。
3. **每一次合并到发布分支，必须关联到 `决策约束/` 或 `交付件/` 下的文件**。
4. `doc/决策约束/` 由人维护，AI 只读。AI 有异议只能在任务记录的「决策记录」一节提出。
5. `code/` 之外的文件（如 `scripts/`）不受规则 2 约束——**豁免由目录路径决定，不由判断决定**。

> 规则 5 的措辞是刻意的。豁免条件必须是机器一查就知的客观事实（文件在哪个目录），
> 不能是"这算不算脚本"这类需要判断的问题。任何需要 AI 自行判断"我该不该被监管"的规则，
> 都会在短期内退化成不存在——模型会倾向于用约束最少的路径解释自己的任务。

## 上下文即资源（本方法论的核心）

人的核心资源是时间，所以人的工作量按人/天排。**AI 的核心资源是上下文与注意力**，
所以 AI 的工作量单位是：**这个任务的交付件能否在一个 session 的注意力周期内闭环。**

一个 session 的生命周期：

| 阶段 | 状态 | 对策 |
|---|---|---|
| 前段 | 注意力最好，快速进入状况 | 用它做需要理解全局的工作 |
| 中段 | 有偏移，但前文提供了场景，理解意图反而更强 | 适合执行已验证过的方案 |
| 后段 | 偏移 + 上下文混淆，意图理解变差 | 不要再开新战线 |
| 终止 | 上下文到极限，无法沟通 | 已交接完毕 |

**AI 不会突然离职，它的离职是可预测的**——这就是为什么每个任务都必须声明上下文预算
（`context_budget`），并且必须在到达 `handoff_at` 之前完成交接。
交接不是"离职前一个月临时整理文档"，而是**把文档先行作为默认工作方式**：
因为 session 这个"员工"离职率极高、在职周期极短、工作能力很强——适合这种团队的工作方式只有一种。

### 落地机制（以及它做不到什么）

这套东西不指望你记得交接。三个 hook 各管一段，但能力边界必须说清楚：

| 机制 | 事件 | 能做什么 | 不能做什么 |
|---|---|---|---|
| 现状注入 | `SessionStart` | 把决策约束、未结任务、压缩前快照送进新会话；无未结任务时完全静默 | 只是提供信息，不构成约束 |
| 交接催办 | `Stop` | 有 code/ 提交但交接说明为空时，阻止会话结束一次，逼出交接文档 | 每 session 只触发一次；不代替判断 |
| 压缩前落盘 | `PreCompact` | 把状态快照写到磁盘，供压缩后重注入 | **无法注入指令、无法引导摘要**——所以它做不了"强制写交接文档" |
| 机械校验 | `PreToolUse` | 拦截未关联任务记录的提交、未关联交付件的合并 | 只管 commit/merge，不管你怎么写代码 |

> `PreCompact` 那一条是查证过官方文档后改的：它只能阻断压缩，而阻断在上下文超限恢复的场景下
> 会让当前请求直接失败。所以真正"逼出交接文档"的是 `Stop`，`PreCompact` 只负责不让状态蒸发。

## 子命令

用户以 `/ai-dev-flow <子命令>` 调用。

| 子命令 | 作用 | 类别 |
|---|---|---|
| `初始化` | 生成 code-doc 结构、CLAUDE.md、项目级 hook | — |
| `启动 <需求>` | 分类路由 → 建任务记录 / 吐决策待办 | 分派 |
| `预算` | 把需求切成"一个 session 能闭环"的粒度 | 管理类 |
| `交接` | 生成交接说明并写回任务记录 | 执行类 |
| `验收` | 逐条对照验收标准，未达标显式列出 | 管理类（人判定） |
| `状态` | 现状总览：决策约束 + 未结任务 + 结构校验 | — |
| `复盘` | 用全新上下文的 subagent 审计本次会话合规性 | — |
| `变更 <变更内容>` | 需求变更传播：升版本 + 标记 stale + 重验清单 | 管理类 |

### `初始化`
在**目标项目**里执行：

```bash
bash ${CLAUDE_SKILL_DIR}/assets/install.sh project .        # 或 <项目路径>
```

生成 `code/`、`scripts/`、`doc/{决策约束,交付件,任务记录,error}/`、各目录 `索引.md` 与 `_模板.md`、
项目 `CLAUDE.md`、`.claude/settings.json`、`.claude/settings.local.json`（状态栏）与 `.claude/hooks/`。

已有文件默认跳过并报告，不会覆盖；需要覆盖时加 `--force`。
若用户还没装 skill，改用本仓库的 `bin/install.sh`，用法相同。

**装完必须提醒用户两件事**：
1. 要在 Claude Code 里接受该目录的工作区信任对话框，否则 hook 不会运行（`-p` 模式除外，它不看信任）
2. hook 以完整用户权限执行 shell 命令；若把 `.claude/` 提交进仓库，别人在未信任目录下
   用 `claude -p` 跑时这些 hook 仍会执行

### `启动`
1. 判定分类（见第一原则），**明确说出判定结果和理由**
2. 属于管理类 → 产出决策待办文档草稿，**不要**创建任务记录，**不要**开始实现
3. 属于执行类 → 检查是否已有 `doc/决策约束/` 覆盖该需求；没有 → 先停下来要人补
4. 创建 `doc/任务记录/task-NNNN-<slug>.md`（用模板，ID 取现有最大值 +1）
5. **验收标准一栏留空并明确请人填写**——不得自行拟定，不得用"功能正常"这类不可判定的措辞
6. 声明上下文预算，判断是否超出一个 session；超了就建议拆

### `预算`
输入一个需求，输出若干任务记录草稿。判定标准只有一条：**交付件能否在一个 session 内闭环。**
过大就拆，拆到每个任务的 `context_budget.files` 可以明确列举为止。
**注意**：这是管理类工作，你输出的是拆分提案，拆法由人定。

### `交接`
按模板「交接说明」一节填写。要求：
- 写给"下一个 session 这个新员工"，不是写给自己的备忘录
- 不得出现"如上所述""前面提到的"这类依赖本次对话才成立的表述
- 「踩过的坑」必须填：试过但走不通的路，避免下一个人重走
- 填完更新 `status`

### `验收`
逐条对照验收标准，格式：

```
✅ <标准> —— 证据：<文件:行号 / 命令与输出 / 交付件章节>
❌ <标准> —— 未达标。现状：<…> 差距：<…>
⚠️ <标准> —— 无法判定。原因：<…>（不得自行判定为通过）
```

**未达标与无法判定必须显式列出，不得静默略过。** 最终判定由人做，不由 AI 做。

### `状态`
一屏输出：生效中的决策约束清单 + 未结任务及其状态 + 结构校验结果（缺失的文档、孤儿提交）。
保持简洁，这是给人看的仪表盘。

### `复盘`
**审计者必须是全新上下文的 subagent**（用 Agent 工具启动），它只读：
本 skill 的 `references/合规检查清单.md`、`doc/` 现状、`git log`/`git diff`。
**不把本次对话过程给它**——它没有"我当时为什么这么做"的记忆，也就无法为当事方自我辩护。
这与本方法论"完全质疑"的立场一致：审计权不交给当事方。

输出写入 `doc/error/<YYYY-MM-DD>-<scope>.md`，每条违规归因到 **执行违规** 或 **规则歧义**。
这两类的修正动作完全不同（加 hook vs 改措辞），必须分开，否则迭代会一直改错东西。

### `变更`
需求变更时（本方法论刻意保留的风险入口）：
1. 在 `doc/决策约束/` 对应文件上升 `version`，追加「变更记录」，**由人确认**
2. 扫描 `refs_decision` 引用了该决策的交付件，把它们标记 `status: stale`
3. 生成重验清单：哪些交付件需要重新验收、哪些任务需要重开
4. **不自动修改任何交付件内容**——先出清单给人看

---

## 禁止事项

- 不得自行修改 `doc/决策约束/` 下任何文件
- 不得自行拟定或修改任务的「验收标准」
- 不得把 `status: draft` 的决策改成 `active`
- 不得在管理类问题上直接给结论而不给选项对比
- 不得用"功能正常""已测试通过"作为验收证据
- 不得静默略过未达标的验收项
- 交接说明不得依赖本次对话上下文才可理解
