# 团队模式设计

> 分支：`experiments` · 状态：**设计中，逐节固化** · 日期：2026-09-25
> 本文是这套东西的单一事实来源。实现与本文冲突时，先改本文再改实现。

---

## 0. 这份文档在解决什么

原 `ai-dev-flow` 是一套面向**人机结对**的流程规范：人在场，hook 在交付节点拦截，把偏差拉回来。
它有效，但有一个致命问题——**人无法离开机器**。

本文描述把它改造成**无人值守的 agent 团队**：需求与决策前置，开发期人离线；
控制权靠四个结构性控制点保住，而不是靠"人在场"。

### 0.1 为什么原设计会把人锁在机器上

不是实现 bug，是**机制形态**决定的。

原设计的前提是"单个 session 长对话会漂移"（见 `INTRO.md` 的 session 生命周期一节）。
既然漂移在过程中累积，就必须在过程中拦截。而拦截的语义是**把人叫到现场**：

- `check-commit.sh` / `check-merge.sh` 用 `PreToolUse` deny，deny 需要人当场处理；
- `stop-handoff.sh` 更直接——它靠**阻止会话结束**把文档逼出来（`README.md:112`）。

于是每个关键节点都要人在。这是"用补偿装置对抗漂移"的必然代价，不是可以调参解决的。

### 0.2 前提变了，补偿装置就该收缩

subagent 改变了前提：每个角色一个有界上下文。**"单个上下文漂移到失控"在团队模式下基本不存在**——
角色调用结束，上下文就结束了。

所以机制重心从**过程中拦截**移到**入口处约束**：开跑前把规则写全，跑起来之后不需要有人盯着。

### 0.3 但代价也变了，必须一起承担

上下文隔离消灭了漂移，引入了新的失效模式：**N 个角色各自持上下文、读同一份文档，会有 N 种理解。**
单 session 时"我前面说过"能兜住的东西，隔离后兜不住。

> **隔离把"漂移"换成了"歧义"。**

所以前置产物必须是**结论式、可求值式**的，不能是散文：写成「若 X 则 Y」「命令 + 预期输出」。
散文只留给「理由」节——`skill/assets/templates/决策约束.md` 里本来就写着"这节不是给 AI 看的，是给未来的你看的"，定位恰好对上。

**前置做得越彻底，对产物确定性的要求越高。这两件事必须一起做，不能只做一件。**

## 1. 贯穿全篇的一条线：把判断换成查表

原设计里已经有过一次这样的胜利，写在硬规则 5 的措辞理由里：

> 豁免条件必须是机器一查就知的客观事实（文件在哪个目录），不能是"这算不算脚本"这类需要判断的问题。
> 任何需要 AI 自行判断"我该不该被监管"的规则，都会在短期内退化成不存在。

团队模式把这条原则推广到**全部新增的决策点**。每当设计里出现"由 AI 判断 X"，
就重写成"由某个客观字段 / 路径 / 集合的成员资格决定 X"。

本文每处决策都标注 **[查表]** 或 **[判断]**。**目标是把 [判断] 压到 0**，
压不掉的地方必须显式写出理由和代价——本文中只有三处：[判断]1 预算切分、[判断]2 "预期"档、[判断]3 取证裁决。

### 1.1 通则：不是禁止判断，而是禁止**不可见**的判断

> **任何判断落地成一条记录，就可以被审计、被复盘、被固化成下次的判据。**

这条通则把层 3 双轨、裁决记录、判据生长三个机制串成了一个东西。

## 2. 六个角色 + 两层工人

每个角色的边界由四件东西定义：**输入、输出、禁止事项、唯一异常出口**。

| 角色 | 输入 | 输出 | 禁止 | 异常出口 |
|---|---|---|---|---|
| **需求分析师** | 用户原话 | 尽调文档（目标 / 非目标 / 开放问题 / 风险）+ 决策约束草稿 + 技术栈 | 不写 `code/`、不下结论 | — |
| **rule-manager** | 尽调产物 + 各角色回执 + 待裁项 | 裁决记录、授权行使、监护 | 不写产品代码、不写需求 | 升级到人（仅限不可逆清单） |
| **设计师** | 已冻结的需求 + 决策约束 | 页面设计 + 结构说明 | 不改需求、不定接口字段 | 决策记录 |
| **develop-manager** | 任务记录（验收标准已批）+ 设计稿 | **接口文档** + 交付件 | 不写 `code/`（机械上做不到）、不得改接口文档去迁就实现 | **决策记录 + 停下** |
| **impl-worker**（manager 派） | 接口文档 + 一份窄任务 | `code/` + 报告 | 不改接口文档、不碰边界外 | **决策记录 + 停下** |
| **test-manager** | 交付件 + 验收标准 | 测试报告（覆盖率 + 变异 + E2E） | 不跑测试、不写 `code/`、不软化判定 | 决策记录 |
| **test-worker**（manager 派） | 待测范围 + 证据形态 | **命令 + 实际输出** | **不得为了让测试通过而改 `code/`** | 决策记录 |
| **秘书** | 待批队列 / 待裁队列 | 人可读的批次清单 + 审批回执 | **不得给推荐结论**、不得修改队列项内容 | — |

后两个是**工人层**，由各自的 manager 动态派生，卡名带前缀（`impl-` / `test-`）。
拆成两层的理由见 §2.5，`code/` 为什么能因此变成白名单见 §2.6。

### 2.1 执行角色的"不判断"需要一个唯一异常出口

要求执行角色不含判断动作，就必须同时给它出口。不给出口，它会把"判断"降级成"悄悄自行权衡"——
这个降级不可观测，正是方法论最不能接受的那种失败。

唯一合法出口是既有的「决策记录」节：**停下 + 记录，不选择**。这是流程，不是判断。

### 2.2 分类动作必须外移

原 `SKILL.md` 的第一原则是"先分类，再动手"，由模型自己判定请求属于管理类还是执行类。

**团队模式下这个动作必须移出执行角色**。`impl-worker` 收到的输入必须已被上游判定完毕：
验收标准已批准、决策约束已 active、任务已在任务记录里建好、**接口文档已冻结**。

否则 `impl-worker` 内部必然出现 `if 管理类 → 出选项对比 / else → 写代码` 这种分支，
而这正是"把该不该被监管的判断权交给被监管者"。

### 2.3 测试角色（test-manager + test-worker）的两条硬要求

**（a）"单测是否真的测到"必须是数字，不是印象。** 这件事有两个层次，混在一起就会被糊弄：

- **覆盖率**证明"这行代码被执行到了"——客观、必然可测，作为最低门槛；
- **变异测试**证明"断言真的能抓住 bug"——覆盖率高的测试仍可能全是 `expect(true).toBe(true)`，
  mutant kill rate 是客观数字，对关键模块作为加强项。

**（b）测试角色不得为让测试通过而修改 `code/`。** 否则裁判兼运动员。
**属硬限制，落 hook，不落身份卡**（见 §9）：`code/` 的写权限白名单里没有 `test-*`（§2.6），
测试产物一律写 `tests/`。

E2E 部分要写明能力边界：环境起不来时报告「**无法执行**」，不是「跳过通过」。

### 2.4 所有角色对人交互都必须经主会话转达

**已核实**：subagent 的工具池里**没有 `AskUserQuestion`**。这不是设计选择，是平台的硬约束。

所以角色与人之间不是直接的对话关系，而是：

```
角色 --产出问题--> 主会话 --AskUserQuestion--> 人 --回答--> 主会话 --回执--> 角色
```

对需求分析师影响最大：它**不能直接提问**，必须把问题结构化地交回主会话。
这一条同时也解释了为什么主会话必须存在——它不只是编排者，也是**唯一的人机通道**。

---

### 2.5 开发与测试拆成两层：manager 决定"怎么派"，工人只做"被派的那一份"

原设计里 `developer` 一个人从"读需求"干到"提交代码"。团队模式下这不成立，理由有两条：

**（a）一份任务里混了两种性质的工作。** "定接口契约"是**收敛**动作（N 个工人的读法要收敛到一份文档），
"实现某一部分"是**发散**动作（可以并行、互不可见）。放在一个角色里，这两件事会互相污染——
它一边写着契约一边已经在想自己那部分怎么实现了。

**（b）技能装配需要有人负责。** 后端 python、前端 react、黑盒/白盒/反例测试，各自该配不同的能力 skill（§2.7），
而**派发时才第一次知道要用什么技术栈**（尽调期只定到技术栈这一层，模块级分工要到接口文档冻结才有依据）。
这个匹配动作必须有具名角色负责，否则没人做，或者每个工人各自去猜。

于是：

| 角色 | 只负责 | 不负责 |
|---|---|---|
| `develop-manager` | 出接口文档、按技术栈配技能、把任务切窄派给 `impl-*`、对接所有结果并按接口文档调通 | **写码**、验收自己的活 |
| `impl-worker` | 拿到一份窄任务 + 一个技能，把它做完并落盘 | 改接口文档、跨模块改动、决定自己该用什么技能 |
| `test-manager` | 决定**测什么**（先读验收标准再读代码）、配技能、派 `test-*`、把碎片证据汇成逐条对照的报告 | **跑测试**、改 `code/` |
| `test-worker` | 执行被派的那一类测试，出**命令 + 实际输出** | 改 `code/`、改测试去让实现通过、写汇总结论 |

**"第一次择决"落在 test-manager 身上**：拓扑取「单 worker + 一个大测试 skill」还是
「黑盒 / 白盒 / 反例各一个 worker 各配一个 skill」，是**问人**决定的一次选择，
之后沿用，不每轮重问（`aidf-verify` §1）。默认取单 worker——省上下文，也少一层有损中继。

### 2.6 `code/` 的写权限是**白名单**，凭据是卡名前缀 **[查表]**

这条是本设计里最值得单独说的一处，因为它把一个**承诺**变成了一个**做不到**。

原设计里"tester 不得改 `code/`"是靠 hook 黑名单实现的：枚举不能写 `code/` 的角色，命中就 deny。
加入工人层之后这个形态立刻失效——**派发出来的工人名字是动态的**，
`develop-manager` 可以派 `impl-order`、`impl-pay`、`impl-whatever`，黑名单永远列不全。
列不全的后果不是报错，而是**静默扩散**：没被列进去的名字一律放行。

所以反过来定：

```
code/ 可写 ⟺ agent_type 以 impl- 开头（主会话不受限）
```

- "谁在写码"退化成一次**前缀查表**，不需要枚举任何人。
- `develop-manager` 成了管理者而不是实现者，**不是因为它守纪律，而是因为它写不了**。
- 代价是刻意的：随便派个通用 subagent 去改代码会被拦。正确做法就是派 `impl-*` 卡
  ——这也正是"每个角色一张卡"的意义所在。

**副作用（好的那种）**：旧版角色卡若还留在机器上，用旧名启动的角色会**撞上 deny 并被告知原因**，
而不是悄悄绕过所有边界检查。`bin/install.sh` 因此会主动检测并警告残留的旧卡（不自动删——删用户目录里的文件要人点头）。

### 2.7 技能装配：规则 skill 之外，还要有能力 skill

`aidf-*` 这七个是**规则 skill**——它们定义"这件事该怎么做"。它们不能告诉一个 python worker 怎么写 python。

> **规则 skill 失效 → 流程跑歪，看得见。能力 skill 缺失 → 流程照跑，产出悄悄不合框架惯例。**

后者更危险，因为它不会在任何检查点显形。所以装配要**在启动团队时由人经结构化选项决定**，
而不是等 worker 自己觉得缺什么。

三个设计要点：

| 要点 | 做法 | 理由 |
|---|---|---|
| **分两个时刻装配** | 角色级（启动时问人）、任务级（manager 派发时查表） | 启动时**不可能**知道要用什么技术栈——尽调还没跑 |
| **双通道 + 装配后自检** | 写 `SKILL.md` 进已存在的 skills 目录 → 同会话生效；走插件 → 本会话用不了，需人敲 `/reload-plugins`。**"调用过一次且成功"才算生效** | 见 §19 的已核实事实；不许说"应该已生效" |
| **由 subagent 去装** | 主会话不亲自装 | 安装日志、错误、目录枚举对编排者是纯噪音 |
| **三档选择，且第三档要给风险** | 装推荐项 / 自定义 / 什么都不装直接跑 | 第三档的风险是"框架惯例层面的缺陷——**它不会在验收标准里显形**"，必须当面说 |

推荐清单是**人可编辑的数据**（`doc/技能装配.md`），带 `核实状态` 列
（`已核实存在` / `人指定` / `未核实`），**不预置无法核实的条目**——
给团队塞一份"看起来有来源的猜测"比留空更糟。详见 `aidf-equip`。

## 3. 前置：分三层，且承认第三层不能前置

尽调的目标不是"决策全部前置"，而是**把决策推进层 1 和层 2，让层 3 变成低频事件**。

### 层 1 · 可前置的需求与决策

技术栈、模块边界、接口契约、优先级、验收标准。这些能在动手前穷举，尽调阶段定完。主要工作量在这里。

「验收标准必须在执行前存在、由人写或人批准」这条不可妥协的前提**没有变**，
只是时间点前移：从"每个任务执行前写"变成"尽调阶段一次性写完全部任务的验收标准"。

### 层 2 · 判据：**不是尽调产物，是复盘产物**

最初的设计是"尽调阶段由人预先写一份判据集"。**这个设计被否决了**，理由：

> 层 3 事件的存在本身，就证明了预先穷举不可能。再加一层判据集去兜住层 3，
> 只是把"前置"又往后推一层，治标不治本——还是想用一个前置动作去覆盖不可预知的东西。

改为自底向上生长：

```
尽调（人写笼统授权）
    ↓
rule-manager 先查已固化的判据 ── 命中 → 直接裁决
    ↓ 未命中
取证裁决
    ↓
人回来后推翻 / 维持
    ↓ 推翻
把这次的裁决依据固化成一条判据 ──→ 下次同类问题不必再取证
```

**判据集是经验的固化，不是预测。** 这与方法论原有的"验证 → 完善方法论"是同一个回路，
只是这次迭代的对象从 hook / 措辞变成了**裁决能力**。

### 层 3 · 不可预见的

只能在执行中暴露的（真实数据上性能不够、这个需求其实用户不想要、有笔技术债必须先还）。
**这一层不能前置，因为信息还不存在。** 硬要前置只会得到假的确定感。

处理方式见 §4；还有一个专门的边界动作见 §5。

## 4. 层 3 的双轨制

### 4.1 轨道判据：`blocks` 字段是否为空 **[查表]**

每条待裁项必须声明它阻塞了哪条验收标准：

```yaml
blocks: [task-0002#验收标准-3, task-0005#验收标准-1]
```

- `blocks` **非空** → **核心轨**：交 rule-manager 裁决后继续推进
- `blocks` **为空** → **非核心轨**：落盘入队，等人回来

判定不看内容、不看重要性、不需要判断，**只看这个字段是不是空的**。

**为什么必须这样定**：如果让 agent 自己判"这个不核心，先记下"，它会稳定地倾向约束最少的解释——
这是硬规则 5 要防的同一个失效模式。

**"非核心"的定义是"当前无任何验收标准依赖它"**，所以延后它天然安全。
唯一代价是：如果日后出现依赖，会产生返工——而这正是 §4.4 升级路径要付的钱。

### 4.2 核心轨：rule-manager 的裁决权及其合法性来源

核心轨交 rule-manager 裁决，直接撞上方法论里"AI 不能为后果负责"这一条。不打算抹平它，但要给它一个可用的形态：

> **不能担责的实体，只能被授予可撤销的权限。**

可撤销性**必须是结构性的，不能是条件性的**（门槛方案已否决，见 §4.3）。两个不需要判断的机制：

**（a）裁决的物理边界是合入发布分支，而这个动作归人。**
硬规则 3 已规定 merge 到发布分支必须关联 `决策约束/` 或 `交付件/`，而这两者由人维护。
所以无论 rule-manager 裁决多少次，**只要它不能合入，它的全部影响都封在分支里**。
人回来一次合并，不满意就丢分支。**可撤销 = 丢分支**，不需要判断某次改动够不够大。

**（b）真正不可逆的动作，用枚举清单拦**，见 §6。

### 4.3 为什么没有"停下等人"的门槛

**任何门槛本身都是一个判断**：要么 AI 判"这算不算大"（等于让它划自己的监管边界），
要么人判（人还是得在场）。**门槛这个机制形态是错的，不是取值问题。**

**返工的性质要说准**：分支隔离保证了错误在合入前会被抓到，所以返工的**绝对风险没有变大**，
变大的是**发现得晚**。因此代价是**已投入的工作量沉没**，不是不可逆损害。

由此得到一条可直接用的推论：

> **返工成本的上界 = 人回来一次的间隔。**

所以不需要门槛，需要的是**调节回访频率**。频繁回来 = 单次沉没小但打扰多；少回来 = 打扰少但单次沉没大。
**这是人自己的旋钮，不涉及任何判断。**

回访时机有客观信号 **[查表]**：**非核心队列的长度**。积压到阈值就是"该回来看一眼了"的提示——
这不是门槛（不是"改动大到就停"），是纯观测提示，不阻塞任何东西。

**返工有四个来源，每一个都该在 §8 的归因表里找到位置：**

| 返工来源 | 归因到 | 修正动作 |
|---|---|---|
| 裁决选错 | 尽调不可及，但判据可覆盖 | 补判据（推翻率驱动） |
| 非核心项漏依赖 | 尽调可及但漏了 | 补尽调检查清单 |
| 歧义累积（主要来源） | 规则歧义 | 改措辞 → 产物可求值化 |
| 外部现实不符 | 两者都不可及 | 接受，度量频率 |

**找不到位置的返工，说明归因体系有缺口**——那才是真正要警惕的信号。

**唯一补不上的一种**：人批的需求本身后来被证明是错的。原来人机结对时人在节点上能察觉，
现在察觉不了。它不产生返工，产生**方向推翻**，而分支隔离正好兜住了它（丢分支）。
**结论：前置消灭的是方向性返工，不是全部返工。**

### 4.4 "非核心转核心"不是判断，是引用出现 **[查表]**

非核心项被延后，直到某条新出现的验收标准引用了它——那一刻 `blocks` 不再为空，它自动就是核心项。

**所以不需要给 rule-manager 一个"判断是否升级"的权限，只需要让它检测引用。**

若确实需要主动升级（例如它预判"这迟早要出问题"），那必须是**显式动作**：
产出一条新记录、标记 `escalated`，并写明理由。

### 4.5 取证：rule-manager 是主持人，不是决策者 **[判断]3**

朴素形态"收集其他 agent 的信息后做出合理决策"**不可接受**——那是黑箱判断。
可用形态是把**判断**改写成**取证**。三条硬约束：

1. **取证义务**：不得单独决断。必须征询受影响角色，回执是结构化的：
   「我的方案会破坏什么 / 我的替代方案 / 我缺什么信息」
2. **征询对象由规则算出，不由感觉决定 [查表]**：由 `blocks` 的引用 + 授权范围的路径交集推出"谁受影响"。
3. **异议留痕，不可删除**：有人反对，反对意见进裁决记录，rule-manager 无权抹掉。

配套判据：**rule-manager 决定的不是"什么是对的"，而是"这个问题该由谁提供什么证据"。**
前者是判断，后者是程序。**残留的判断成分已标注 [判断]3**，靠"必须留痕 + 可撤销"限制其影响面。

### 4.6 裁决记录规格

每次核心轨裁决产出一份记录，至少含：

| 字段 | 内容 | 用途 |
|---|---|---|
| `type` | 问题类型（须命中总授权里的类型，见 §7.1） | 越权校验 |
| `paths` | 实际改动的路径范围 | 越权校验 + 影响面 |
| `based_on` | 依据：命中的判据 ID，或取证回执摘要 | 复审依据 |
| `dissents` | 反对意见（不可删除） | 复审依据 |
| `blast_radius` | 影响面报告：牵动了哪些交付件 / 任务 | 人回来快速判定 |
| `reversible_by` | 回滚边界（分支 / commit 集合） | **可撤销性的物理落点** |
| `no_forecast_reason` | 为什么尽调时没预见到 | 喂给 §8 的归因 |

**裁决记录 = 复审依据，改动范围 = 回滚边界。**

### 4.7 非核心轨：队列 + 保守默认

- **保守默认 = 不做**。不做是可逆的，所以即使人不在场，团队也不会卡死，只是那件事等。
- 待批队列**必须可批量审批**：人离线一段时间后回来看到 20 条散项，会干脆不看。
  队列要有稳定 ID（人才能说"批准 1、3、5"）和分组（"其中 3 项同属认证模块"）。

## 5. 离开声明

人在离开前主动声明"我要走了"。这个动作把"回来时被队列困住"改成"离开前主动清空"。

### 5.1 它不是新机制，是**队列的批量预填充**

三档映射到既有机制，不新发明：

| 档 | 判据 | 归属 |
|---|---|---|
| **当前需要** | 现在就被阻塞（`blocks` 非空且已到那一步） | 核心轨，**人现在定** |
| **预期** | 将来会阻塞（`blocks` 可预填，但还没到） | 人可现在就定，或授予 rule-manager 裁决 |
| **不确定** | 不知道会不会阻塞 | 非核心轨，入队 |

判定还是 `blocks` **[查表]**。**离开声明 = 在离开那一刻，把所有待裁项往后推演一遍并落盘。**

### 5.2 每条疑问必须带两样东西，否则不许进清单

不设这条约束，agent 就有动机**把所有事都列成不确定**——将来做错了可以说"我当时列过了，你没定"。
这是**责任转移**。

1. **保守默认**：没人定的话我打算怎么做（本来就是 §4.7 对非核心项的要求，只是提前到这一刻）
2. **事实锚点**：这条疑问基于哪个已存在的产物（文件 / 交付件 / 验收标准）

第 2 条把"根据当前的进展"落成了机制：**疑问必须锚定到已产出的东西，不能是基于想象的提问**。
两样都缺 → 不许进清单。保守默认要求让"列举疑问"的成本上升，事实锚点让每条可被 hook 核查。

### 5.3 人只处理"当前需要"那一档

**这一条是防退化的关键。** 如果人必须答完清单里每一条才能走，
**离开声明就变成了"答完题才准走"**，反而把人锁住——正是要消除的东西。

所以：**人只处理核心档，其余走默认或授权。** 人有权直接说"剩下的全走默认"，一句话结束。

### 5.4 它顺带产出：针对具体问题的**临时授权**

"预期"档里，人可以选择"这个留到那时候让 rule-manager 裁决"。那一刻产生的是**针对具体问题的授权**——
比尽调阶段的笼统授权精准得多，正好填上 §7 里"类型级授权"与"具体裁决"之间的空档。

若同类预期反复出现，它可以**固化成类型级授权**——与 §3 层 2 判据集的生长方式同源，都是自底向上。

### 5.5 职责分工：产出归分析师，呈现归秘书

- **需求分析师**：收清单、分档、产出三档结果（尽调本职）
- **秘书**：呈现给人、记录裁定、记录临时授权

需求分析师**产出**清单，秘书**呈现**清单。这样"审批类交互唯一入口是秘书"不破——
否则需求分析师自己也成了人机接口。

### 5.6 它是尽调质量的**即时检验**

**离开声明产生的"当前需要"条数 / 任务数** —— 这个数字高，说明尽调没做够。
它的价值在于**测出来的时机**：此时错误还便宜（大不了人现在定一下），
而不是等回来时发现已经返工了。

### 5.7 触发与否都留痕

人可以不触发。但**两种都记录**：触发了记清单与裁定，没触发记一条"本次离线无声明"。
轻量，但让这个选择变得可见、可统计——否则"永远不触发"会导致"回来被队列困住"毫无预警。

### 5.8 一处诚实说明

**"预期"档含判断成分，已标注 [判断]2**，因为预测"将来会阻塞"本身就是判断。消不掉，用两个方式限制影响面：

- 必须附客观依据（哪条验收标准可能受影响），无依据的降级到"不确定"档
- **它只是建议，不是判据**——人对它可以全盘不理，直接留到那时候裁决

最坏情况是白列几条，不造成系统性影响。

## 6. 不可逆动作清单

真正不可逆的工程动作很少，而且**可以穷举**：删数据、对外发布、push、动凭证、调用有外部副作用的接口。

- **判据是"这个动作在不在清单里" [查表]**，不是"这次改动大不大"。
- **清单在尽调阶段产出**，放在 `doc/决策约束/`（人维护、AI 只读）。
- 撞上清单外的不可逆动作 → 保守默认 **不做**，不阻塞其他推进。

与 §4.3 的"无门槛"不矛盾：门槛是"如果大就停"（判断），清单是"如果在集合里就停"（查表）。
集合有限、预先写、客观。

## 7. 授权：二维，放决策约束

### 7.1 授权到**问题类型**，所以类型必须闭合且成员可判定

授权粒度是「问题类型」，于是"这次属于哪个类型"成了新的判断点。
**如果 rule-manager 自己分类，它会选授权最宽松的那个类型**——还是"被监管者选择监管规则"。

所以类型的成员资格必须是客观事实，每个类型带**检测信号**（什么事实能证明"这次属于这个类型"）：

- ❌ 「实现细节问题」——没有边界，任何事都能塞进去
- ✅ 「第三方依赖版本冲突」——manifest 冲突或报错命中固定模式
- ✅ 「同一验收标准下两个模块的接口字段命名不一致」

信号不存在 → 不属于该类型 → 走 §4.5 取证。

**副作用（是好的）**：类型就是判据集的分组名。总授权（人写、按类型、有限稳定）与
判据（复盘长出来、按类型累积）自然合成一个结构。
"某个类型下累积了太多推翻记录"本身就是信号——说明这个类型的授权给早了，或该拆。

### 7.2 两层权限，解决"AI 只读 vs AI 要产出授权"的矛盾

`doc/决策约束/` 是人维护、AI 只读（硬规则 4），而 rule-manager 要在裁决时**产出**授权。矛盾解法：

| | 谁写 | 内容 | 权限 |
|---|---|---|---|
| **总授权** | 人（尽调阶段 / 离开声明） | "类型 T 下 rule-manager 可自行裁决" + 授权路径范围 | AI 只读 |
| **本次行使** | rule-manager（裁决时） | 这一次实际授权到哪些路径 | 写在裁决记录里，**不写进决策约束** |

**越权校验 [查表]**：裁决记录的 `type` 必须命中总授权的类型集合，
`paths` 必须是某个总授权路径的前缀子集。两者都是集合成员资格，hook 直接查得出。

于是"授权本身就是决策"这个洞察保住了（总授权由人定），而 AI 不能自己扩大自己的授权。

## 8. 错误归因：从两类扩到五类

原设计把违规归因成两类，理由是**归因错误会让迭代方向完全跑偏**（`references/合规检查清单.md`）：
把规则歧义当执行违规，你会不停加 hook 而问题依旧；反过来，你会把规则越写越长而模型照样不遵守。

层 3 事件需要同一套纪律下的新类别，因为**它们的修正动作都不一样**：

| 归因 | 含义 | 修正动作 |
|---|---|---|
| 执行违规 | 规则清楚，AI 没遵守 | 加 / 收紧 hook |
| 规则歧义 | 规则没说清楚 | 改措辞 |
| **尽调可及但漏了** | 信息本可以问到，没问 | 补尽调检查清单（**改流程**） |
| **尽调不可及，但判据可覆盖** | 信息当时不存在，但「若 X 则 Y」本可以预写 | 补判据集（**改规则**） |
| **两者都不可及** | 真意外 | 接受，只度量频率 |

三类递进的修正动作分别是「改流程 / 改规则 / 接受」。
混在一起写成"复盘发现考虑不周"，就什么都不会改。

## 9. 三层载体：身份卡 / skill / hook

| 层 | 载体 | 承载什么 |
|---|---|---|
| **软限制** | 身份卡（`.claude/agents/*.md`） | 角色视角、职责边界、产出契约、对 skill 的入口白名单 |
| **规则与动作** | 共享 skill（**只存一份**） | 取证流程、裁决记录格式、尽调流程、模板 |
| **硬限制** | hook（`.claude/settings.json` + `.claude/hooks/`） | 可机械校验的一切 |

### 9.1 准入判据：凡是可以写成 hook 的限制，就不该只写在身份卡里 **[查表]**

否则就是"规则在纸上存在、在运行时不存在"（`README.md:48-49`）。

- **硬限制 → hook**：`code/` 只有 `impl-*` 能写（含 `develop-manager`、`test-*` 在内的其余 subagent 一律拦）；
  任何角色不得写 `doc/决策约束/`；`status: draft → active` 只有人能翻（硬规则 4）；
  commit 必带 `task-NNNN`；分支名必带 `task-NNNN`；裁决不得越权（类型 + 路径）；
  队列项必带保守默认与事实锚点；不可逆动作 subagent 不许做。
- **软限制 → 身份卡**：机械校验不了的那些——角色视角、决策记录作为唯一异常出口、
  陈述句而非命令句（`inject-context.sh` 里论证过：命令句会触发模型的 prompt-injection 防御）。

身份卡薄（身份 + 边界 + 入口白名单），skill 厚（规则 + 动作 + 模板），**公共部分只存一份**。

理由是这个 repo 已经吃过"同一处修五次"的亏（`_lib.sh` 的存在理由、`CLAUDE.md` 与 `SKILL.md`
硬规则编号必须对齐的注释）。六个身份卡各自复制一套硬规则，会立刻漂移。

### 9.2 硬限制绝不能写进身份卡——这是平台的硬约束，不是风格选择

**已核实**：从 plugin 加载 agent 时，下列 frontmatter 字段**因安全原因被直接忽略**：
`hooks`、`mcpServers`、`permissionMode`（以及 `initialPrompt`）。

所以"身份卡自带 hook"这条路径不存在。硬限制一律走 `.claude/settings.json` 或 plugin 的 `hooks/hooks.json`。

### 9.3 工具白名单的两个陷阱

- `disallowedTools: "Bash(git push *)"` 会**移除整个 Bash 工具**，不是只挡这条命令。
  要挡具体命令只能用 `permissions.deny` 的 Bash 规则。
- 若 `tools` 里所有条目都解析不到工具，subagent **通常拒绝启动**（"zero tools" 错误）。

## 10. 秘书

它是**人的唯一入口**（见 §2.4 的通道机制），所以是全队里标准最高的角色。

**（a）不得给推荐。** 一旦它说"建议批准第 3 项"，它就在替人做决策——正是管理类的"完全质疑"要禁止的。
产出必须是材料：每项的选项、各自代价、影响面、保守默认、**谁反对过**。
给"通过 / 退回"的选项是对的，给"我建议通过"是错的。

**（b）触发点是"人回到机器"，不是"有人发消息"。**
消息通道是易失的，队列是持久的。**队列文件的存在本身即是信号**，不需要消息机制。

**（c）写权限只有一处**：记录人的裁定（`decided` 字段 + 人的原话）。
队列项的内容它不得修改——否则一个"整理"动作就能悄悄改变人看到的材料，
而人以为自己看的是原始事实。

**（d）它兼任入口路由**（原未决问题，已定）。人回到机器可能做三件事：发布新需求 / 审批队列 / 看进展。
秘书接第一句话并路由：新需求 → 交需求分析师；审批与状态 → 自己处理。

## 11. 队列落盘形态

**每项一个文件 + 一个自动汇总的索引**（人批量审批需要索引，机器状态追踪需要单项文件）。

```
doc/待裁/
  escal-0001.md           单项：type / paths / based_on / dissents / blocks / default / anchor / status
  索引.md                 自动生成的汇总
doc/待批/
  appr-0001.md
  索引.md
```

状态机极小：`open` / `decided` / `defaulted`（走保守默认）。
每项带稳定 ID，人才能说"批准 1、3、5"。

**并发注意 [已核实]**：同一事件的多个 hook **并行执行**，写同一状态文件会有竞态。
队列落盘必须加锁（`flock`），或一律采用追加写（一行一个 JSON）。

## 12. 分支

**要求开发变动必须走分支，且每个分支要有它实现的需求的描述。**

最省事的落地方式，是复用现成的零件：

- **分支名带 `task-NNNN`** → 复用 `check-commit.sh` 已有的 ID 提取与 `task_file()` 伪引用检查，不引入新格式；
- **描述取自任务记录的「目标」节**（非空校验复用 `_lib.sh` 的 `section_empty`）。

**一条必须一起定的规则：一个分支一个任务。** 跨任务的分支会让"这个分支实现了什么需求"不可判定。
如果需要跨任务，说明任务粒度超了——回到"上下文预算"那条规则。

**分支粒度 = 任务粒度**，两者都可机械校验。

## 13. 收口：人的在场窗口

**尽调阶段人要回答需求分析师的提问，人本来就在场。所以尽调产物冻结前的那次确认是免费的。**

| 时刻 | 动作 |
|---|---|
| 尽调期 | 深度参与、给总授权、写不可逆清单、确认冻结 |
| **离开前** | **离开声明：清核心档、给临时授权**（§5） |
| 开发中 | 队列累积 |
| 该回来时 | 队列长度提示（§4.3） |
| 回来 | 秘书渲染、批量审批、推翻率记录 → 固化判据 |
| 收口 | 合入发布分支（唯一由人触发的动作） |

三个时刻都是**边界上的批量动作**，都不打断开发。

控制权靠四个点保住，而不是靠在场：

1. **规则由人定** —— 总授权、不可逆清单、验收标准（尽调期一次）
2. **结果由人审** —— 交付件 + 全新上下文 subagent 审计
3. **异常由人裁** —— 离线队列，批量处理
4. **合入由人触** —— 唯一的物理收口点

### 13.1 尽调 loop 的终止条件

**不能是"需求分析师觉得可以了"。** 这是设计早期唯一一处硬伤，必须改成客观事实：

- 每个被审核角色返回**结构化的 `blocking_questions`**，**全部为空**才终止；
- 每个角色显式**签名**（sign-off 字段非空）；
- 悬而未决的问题只有两个合法去处：`resolved`（附答案来源）或 `accepted_risk`（附 rule-manager 的接受记录）。

"分析师觉得可以了"只能是**触发审核的动作**，不能是**终止条件**。

### 13.2 审核的媒介必须是文档，不是消息

如果每轮把需求向各角色**重述**一遍，N 轮 × 各角色的上下文成本是平方级增长，而且每轮都有重述带来的漂移。

正确做法：尽调产物**落盘**，审核方**读文档**，只输出对当前版本的 diff 意见。
第二轮只需看变更部分。这顺带把"文档先行"从人的纪律变成了 agent 团队的唯一工作方式——
**角色也是高离职率员工，上下文同样有限。**

### 13.3 "聚焦核心需求"的机械实现

rule-manager 在尽调 loop 中的职责是"确保需求聚焦在用户的核心需求上"。客观抓手：

> **需求文档里每一条需求都必须标注用户原话来源**（`来源: "<用户原话片段>"`）。
> 找不到来源的条目，要么删掉，要么显式标记为"AI 建议，待批准"。

与硬规则 5 的动机一模一样：**聚焦由"有没有原话来源"决定，不由"感觉相不相关"决定** [查表]。

## 14. hook 的 fail-open 风险与对策

**已核实，这是本设计最容易静默失效的一处**，必须单独成节。

| 失效模式 | 事实 |
|---|---|
| **超时 = 闸门失效** | `PreToolUse` 上超时的 command hook **不阻断**工具调用，"别指望卡住的 hook 当闸门" |
| **起不来 = 静默失效** | 路径写错 / 不可执行时只是 non-blocking error，动作照常进行 |
| **退出码 1 ≠ 拦截** | 多数事件只有 `exit 2` 才拦；`exit 1` 是 non-blocking error |

这三条合起来，正好构成 repo 最忌讳的那种失败：**看起来有效果**。

### 14.1 对策：拦截 hook 与记录 hook 并联

**已核实这是官方推荐形态**：日志 hook 只做追加写、`exit 0` 不输出决策，与拦截 hook 并行执行；
拦截返回 deny 时，**日志仍会写入**，因为它们已经跑过了。

所以本设计的落地形态是——**每一个拦截点都由两个并联的 hook 组成**：

```
check-*.sh        拦截（deny / exit 2）
log-*.sh          记录（追加写，永不返回决策）
```

好处有两个：拦截失效时事件仍然留痕（可观测），以及队列落盘不必依赖拦截 hook 本身。

### 14.2 配套要求

- 拦截型 hook 必须进 `bin/selftest.sh`，**且必须有一条用例专门测"拦截失效时是否留痕"**。
  理由和 README 里那段自述同源：一个会静默通过的校验，比没有校验更危险。
- 无人值守场景的兜底：`--permission-mode dontAsk` 或 `--permission-prompts none`
  （保证"永不等待输入"）。**注意 `deny` 连 `bypassPermissions` 都穿透，所以拦截本身是可靠的**——
  不可靠的只是"hook 有没有跑起来"。
- 状态文件路径用 `${CLAUDE_PROJECT_DIR}` 拼绝对路径，不要依赖 `cwd`（它跟随 Claude，进 worktree 会变）。

### 15.1 保留并扩展

| 文件 | 改动 |
|---|---|

| 文档结构 | 新增 `doc/待裁/`、`doc/待批/`；其余不变 |

### 15.2 事件的挂载点必须改（原设计挂错了）

**已核实**：

- `SessionStart` 是 **per session**，不是 per subagent。给角色注入现状要用 **`SubagentStart`**
  （它可以用 `additionalContext` 往 subagent 上下文注入）。
- `Stop` 明确是"**主** agent 响应结束"。给 subagent 做收尾强制力必须用 **`SubagentStop`**；
  写在 subagent frontmatter 里的 `Stop` 会被改写成 `SubagentStop`。

所以 §15.1 里"扩展 inject-context"要**挂 `SubagentStart`**，
§15.3 里"降级"的那批要**重新评估挂载点**，而不是原样保留。

**区分 subagent 的可靠字段是 `agent_id`**（只在 subagent 调用内存在），
不要用 `agent_type` 的存在性判断——`SessionStart` 也有它。

### 15.3 降级并限定生效范围

`context_budget` / `handoff_at` / 「交接说明」/ `stop-handoff.sh` / `precompact-snapshot.sh`——
**这一整套是为"单个 session 干到漂移"设计的。团队模式下每次角色调用都是全新上下文。**

不砍掉，但服务对象变了。只有两类还需要它们：

1. **长跑角色**——rule-manager 这种可能跨很多轮的编排者（挂 `SubagentStop`）；
2. **人自己在项目里直接干活**这个残留场景（挂 `Stop`）。

### 15.4 新增

- 待裁 / 待批队列（落盘 + 索引 + 极小状态机 + 加锁）
- 裁决记录格式与校验（§4.6）
- 不可逆动作清单及其 hook
- 角色 × 动作白名单及其 hook
- 八张身份卡（六角色 + 两工人）+ 共享 skill（规则 skill 7 个 + 能力装配 skill）
- 记录型 hook（与每个拦截型 hook 并联）

## 16. 度量指标

| 指标 | 含义 | 用途 |
|---|---|---|
| **推翻率** | 人回来后推翻裁决的比例 | 唯一诚实的质量指标。**事后测得，不需要预先预测**。判据集该长什么的唯一可靠输入 |

| **非核心转核心次数** | 引用升级频率 | 对依赖关系的把握程度 |

比"感觉尽调做得挺细"可靠得多。

## 17. 构型与分发

**已定：跑在交互式 session 上**（`claude -p` 下 agent teams 不会 spawn teammate，且编排复杂度对当前阶段是负收益）。

### 17.1 团队声明卡 = 主会话身份

```
主会话（= dev-team 团队声明卡，用 `claude --agent dev-team` 启动）
   ├── 编排：spawn 各角色 subagent
   ├── 人机通道：AskUserQuestion 只有这里有（§2.4）
   └── 路由：发新需求 / 审队列 / 看进展（§10d）
        │
        ├─ requirements-analyst   (subagent)
        ├─ rule-manager           (subagent)
        ├─ designer               (subagent)
        ├─ develop-manager        (subagent) ──派──> impl-worker / impl-<域>
        ├─ test-manager           (subagent) ──派──> test-worker / test-<类>
        └─ secretary              (subagent)
```

**这也是"通过团队声明卡启动整个团队"的实现**：一张卡把整个会话变成这个团队。

#### 17.1.1 主会话够不着工人层 **（已核实）** [查表]

团队声明卡的 `tools` 里写的是
`Agent(requirements-analyst, rule-manager, designer, develop-manager, test-manager, secretary)`
——一份**白名单**（`Agent(...)` 的括号只在主线程卡里生效，角色卡里写了会被忽略，正好落在这里）。

三个结构性后果：

1. 主会话派不了 `impl-*` / `test-*`，实现与测试的派发**只能**经过各自的 manager。
   这不是省事，是刻意的：否则"谁负责对接""谁负责汇总"会在派发链上消失。
2. 名单里**没有 `general-purpose`**，所以不指定 `subagent_type` 直接调 Agent 会**报错**——
   报错比悄悄派一个无身份的 subagent 强。
3. 因为写码的人必然出自 manager 这一层，`code/` 白名单（§2.6）才立得住。

> **`tools` 绝不能只列 `Agent`。** 到达派发深度上限时 `Agent` 会被运行时收回，
> 若列表因此解析为空，平台会**硬拒绝**启动该 agent
> （逐字报错：`would be spawned with zero tools — refusing`）。所有卡都要至少再带一个工具。

### 17.2 分发层级的拆分，沿用既有原则

原 repo 的拆分理由是"skill 无副作用、hook 会拦你"。身份卡与 skill 同性质，所以：

| 内容 | 装到 | 理由 |
|---|---|---|
| 8 张身份卡 + 共享 skill | 用户级（`~/.claude/agents/`、`~/.claude/skills/`） | 无副作用，不调用什么都不做 |
| hook + 队列结构 + `CLAUDE.md` | 项目级 | 会拦你，必须只在明确启用的项目里生效 |

`bin/install.sh` 增加 `team` 模式承担这件事。

**注意一个分发陷阱 [已核实]**：单独一个 skill **不能**携带 agent。
若日后要打包成 plugin，得走"skills-directory plugin"——在 `.claude/skills/<name>/` 下放
`.claude-plugin/plugin.json`，该目录即以 `<name>@skills-dir` 被当作 plugin 加载，可自带 skills / agents / hooks。

## 18. 它做不到什么

这一节比上面的功能列表更重要——**知道自己能力的边界，是这套方法论自己的要求**。

- **层 3 不能前置**，只能压低频率。任何"决策全部前置"的说法都是假的确定感。
- **没有停下等人的门槛**，代价是返工变成沉没工作量，其上界 = 回访间隔（§4.3）。
- **rule-manager 的判断没有被消除**（[判断]3），只是被约束成可审计的取证过程。
  任何无人值守的系统都必须有一个把信息收敛成动作的环节，那个环节必然含判断。
  区别只在于判断的可见度。
- **"预期"档含判断成分**（[判断]2），只能是建议，不能是判据（§5.8）。
- **上下文隔离带来的"歧义"无法根除**，只能用前置产物的确定性去偿（§0.3）。
  产物越含糊，这套东西失效得越彻底。
- **hook 会 fail open**（§14），拦截失效时不会自己喊。必须有并联记录 hook + 自测兜底。
- **最终验收判定与合入仍由人做**，不由 AI 做。
- **所有角色对人交互都要经主会话转达**（§2.4），这引入了一层转述损耗。

## 19. 已核实的技术事实

来源：官方文档站，逐页核实。**这些是本设计的承重墙，不是假设。**

| # | 事实 | 对本设计的意义 |
|---|---|---|
| 1 | **hook 在 subagent 内触发**，带 `agent_id`（只在 subagent 内存在）/ `agent_type` | rule-manager 的监护可落地 |
| 2 | **subagent 能通过 Skill 工具调用 skill** | "薄身份卡 + 共享 skill"成立 |
| 3 | **agent teams 在 `-p` / Agent SDK 下不 spawn teammate**，且实验性、默认关 | 不基于 agent teams；改用 Agent 工具 + 命名 subagent → §17.1 |
| 4 | **`deny` 立即返回、不挂起**，且穿透 `bypassPermissions` | 无人值守成立 |
| 5 | **"只记录不决策"的 hook 是官方推荐形态**，与拦截 hook 并联 | §14.1 的形态依据 |
| 6 | **`AskUserQuestion` 在 subagent 工具池里没有** | §2.4：人机通道只能在主会话 |
| 7 | **plugin agent 忽略 `hooks` / `mcpServers` / `permissionMode`** | §9.2：硬限制不能写进身份卡 |
| 8 | **`SessionStart` 是 per session；`Stop` 是主 agent 结束** | §15.2：挂载点修正 |
| 9 | **同事件多 hook 并行执行** | §11：队列落盘要加锁 |
| 10 | **hook 超时 / 路径错 / exit 1 都不拦截** | §14：fail-open 风险 |
| 11 | **`disallowedTools` 带 specifier 会移除整个工具** | §9.3 陷阱 |
| 12 | **`Task*` 工具默认只在特定模型上提供** | 队列自己落盘，不依赖它——已躲过 |
| 13 | **subagent 能再 spawn subagent**，默认深度 3（`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`；v2.1.217–218 时为 1） | §2.5：manager 派工人成立。落地时不要依赖默认值，显式设 |
| 14 | **到达深度上限时 `Agent` 被运行时收回**；若 `tools` 因此解析为空 → **硬拒绝启动**（`would be spawned with zero tools — refusing`） | 所有卡的 `tools` 都要至少再带一个工具，绝不只写 `Agent` |
| 15 | **`Agent(...)` 白名单只对主线程卡（`claude --agent`）生效**，角色卡里写括号会被忽略 | §17.1.1：白名单正好落在团队声明卡上 |
| 16 | **`tools` 是白名单时，`Skill` 必须显式列进去** | 每张角色卡都要写 `Skill`，否则角色调不了 skill |
| 17 | **subagent 装的 plugin 本会话不可见**；`/reload-plugins` 是内建 CLI 命令、**模型无法调用** | §2.7：插件通道的最后一公里必须由人走 |
| 18 | **subagent 可闭合的唯一路径**：把 `SKILL.md` 写进**会话启动时已存在**的 skills 目录（热重载，已核实） | §2.7：通道 A；目录不存在则不成立，装配前必须先查 |
| 19 | **`claude plugin install --json`** 成功与失败都返回 JSON（`outcome` / `failureCode`）；`marketplace add` 不接受 `--json` | §2.7：装配的客观判据，不靠"看输出像不像成功" |
| 20 | **skill 优先级：企业 > 个人 > 项目**；plugin 的 skill 带命名空间，不会撞名 | §2.7：装配不覆盖已有同名 skill |
| 21 | **技能正文留在对话里；压缩后每个技能只重挂最近 5000 tokens，共享 25000 额度** | §2.7：装配不是越多越好，早期装的会被挤掉 |
| 22 | **`claude --agent <name>` 能解析用户级 `~/.claude/agents/`**（本机实测：故意给一个不存在的名字，报错里列出的"可用 agent"含全部 9 张自装卡） | §17.1：团队卡装用户级即可被 `--agent` 启动 |
| 23 | **`--agent` 遇到不存在的名字是硬报错（exit 1）并打印可用名单，不静默回退到默认主线程** | §17.1 的启动命令不会"看起来启动了团队、实际会话没被接管" |
| 24 | **`tools: Agent(a, b, c)` 白名单对主线程卡真的拦截**（本机实测：卡里只写 `Agent(secretary)`，请求 `impl-worker` 时工具返回 `Agent type 'impl-worker' not found. Available agents: secretary`） | §17.1.1「主会话够不着工人层」是结构性的，不是约定 |
| 25 | `--agent <agent>` 的 help 原文是 "Agent for the current session. Overrides the **'agent' setting**" —— 即 settings 里还有一个 `agent` 键可以设默认主 agent | 除 `--agent` 外还有一条设默认入口；不建议用（默认值藏在配置里，人看不见当前会话跑的是哪张卡） |

**一处措辞值得注意（已核实但会误导）**：白名单拦截时的报错是
`Agent type 'X' not found. Available agents: <白名单里的名字>` ——
它说的是"找不到"，而 `X` 其实**是**注册过的，只是不在本卡的白名单里。
读起来像拼错了名字，而不是被策略挡住。撞上它时按"不在本卡白名单"理解。

**文档未载明的一处**：settings 级 `Stop` hook 是否在 subagent 结束时也触发。
不依赖它，一律按 `SubagentStop` 设计。
