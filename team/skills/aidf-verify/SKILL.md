# 验证

**一份规则，两个使用者**：test-manager 决定测什么并汇总，test-worker 执行并出证据。

## 0. 两件事，不是一件

**测试不是"跑一下单测"。** 要证明两件事：

1. 单测**真的测到了**目标函数
2. 端到端**真的能跑通**

第 1 件不是"我看了下测试文件觉得没问题"——那是印象。**必须是数字。**

## 1. 测试拓扑：第一次问人，之后沿用（test-manager）

| 拓扑 | 形态 | 适合 |
|---|---|---|
| **单 worker** | 一个 `test-worker` + 一个大的测试技能 | 项目小、上下文预算紧、方法尚未分化 |
| **分工** | 黑盒 / 白盒 / 反例各派一个，各配一个技能 | 模块多、需要并行、每类方法有专门套路 |

默认取**单 worker**（省上下文、少一层有损中继），需要时升级。
问人时把上面那张表**原样给出**，不要简化成"要不要多派几个"。

**决定测什么的依据**（客观，逐条查）：

| 依据 | 决定 |
|---|---|
| 验收标准里的每一条 | **必测**，一条不能少 |
| 改动触及的模块 | 覆盖 + 变异 |
| 接口文档里的错误码 / 边界 | 黑盒：逐个构造 |
| 有并发、超时、重试、金额、权限的地方 | 反例：边界与失败路径 |
| 端到端主路径 | **必测** |

**先读验收标准，再读代码。** 顺序反了就会被实现牵着走——
它做了什么你测什么，而标准里没写的路径永远没人看（见 §7）。

## 2. 配技能（查表）与派发（test-manager）

按 `aidf-equip` §6 查表给每类测试配技能；**匹配不上就写"无匹配"，如实报。**

派发的 prompt 里必须写齐：验收标准路径 + 负责哪几条 + 证据形态 + 技能名 + 产物路径。

**worker 必须把证据落盘。** 派发是**有损中继**——主会话看不到 worker 的 transcript，
"它说测过了"不是证据，**能被人重跑一遍的命令加输出才是**。

## 3. 层次一：覆盖（最低门槛）

```bash
npm test -- --coverage
```

报告里**必须写具体数字**：

| ❌ | ✅ |
|---|---|
| "覆盖率提升" | "`code/order/state.ts` 行覆盖 87%，分支覆盖 79%" |
| "测了主要逻辑" | "`state.ts` 全部 6 个状态转移都有断言；`persist.ts` 覆盖 41%，缺口在错误分支" |

**覆盖率证明"这行代码被执行到了"** —— 客观、必然可测。

## 4. 层次二：变异（关键模块的加强项）

**覆盖率可以骗过去。** 全写成 `expect(true).toBe(true)`，覆盖率照样满。

```bash
npx stryker run --mutate 'code/order/state.ts'
```

`mutant kill rate` 是**客观数字**：它反向验证断言的有效性，不依赖任何人的印象。

```
code/order/state.ts     mutant kill 12/14   （2 个存活：超时边界、并发分支）
```

**存活的那 2 个就是必须写进报告的缺口** —— 它们精确指出"哪条断言是假的"。
这比"覆盖率 87%"信息量大得多。

## 5. 层次三：端到端

单测过了不代表能跑。真的把系统跑起来走一遍主路径。

**能力边界必须如实报。** 环境起不来、依赖装不上、需要真实凭证、需要真实计时器：

```
AC-2 超时 30 分钟自动取消 → 无法执行
  卡在哪：需要真实计时器，当前环境无法把时间推进 30 分钟
  试过：改用 fake timer → 超时值硬编码在 code/order/state.ts，不可注入
  需要什么才能跑：把超时值做成可注入（需先改 code/ → 见决策记录）
```

**不许写「跳过通过」。** 把"没测"写成"通过"，是本团队最危险的一种产出——
**它看起来有效果**，而没有任何人会去复查一个绿色的结果。

**但也不要拿它逃避**：只有真的试过并撞上边界，才算「无法执行」。
没试就写，等于把"我没干"包装成"干不了"。

## 6. 最硬的一条纪律

> **不得为了让测试通过而修改 `code/`。**

`test-manager` 与 `test-worker` 都是裁判，不能兼运动员。

- 发现代码错了 → 写进报告 + 走「决策记录」，**不改代码**
- 需要改代码才能测（如上例的注入 fake timer）→ 走「决策记录」，标明这是为可测性做的改动

这条是**硬限制，落在 hook 里**：`code/` 的写权限白名单里没有 `test-*`，
写了会被拦。**但即使 hook fail open 了，纪律照样成立**——
报告里必须能解释每一行 `code/` 改动，而正确做法是零改动。

**需要写测试文件 → 写在 `tests/` 下。** 测试产物与源码分开，
这条边界才是机械可查的：`test-*` 能写 `tests/`，写不了 `code/`。

## 7. 报告格式（逐条对照验收标准）

不是对照代码意图——那是最容易发生的偷换。

| 验收标准 | 判定 | 证据 | 备注 |
|---|---|---|---|
| AC-1 下单后立即扣减库存 | 通过 | `npm test order.spec.ts` → 14 passed | 覆盖 87% / kill 12/14 |
| AC-2 超时 30 分钟自动取消 | **无法执行** | 需真实计时器 | 替代方案见决策记录 |
| AC-3 并发下单不超卖 | **不通过** | `npm test order.spec.ts -t 并发` → 2 failed | 见决策记录 |

**「不通过」和「无法执行」都必须出现，且都不能被软化。**

一张全是"通过"的报告，如果覆盖率或变异有缺口，**它本身就是要复查的信号**。
不要为了让报告好看而只报通过项——报告的作用是暴露问题，不是结项。

**worker 还要自标弱断言**：用了 `toBeTruthy()` 之类糊过一切的断言，
自己写进"自我标注的弱断言"一栏。覆盖率高而 kill rate 低，就是这个信号。

## 8. test-manager 的汇总与两个角色的边界

**汇总**：worker 回来的是碎片证据，你把它拼成逐条对照的报告。
**worker 说"通过"而没给命令和输出 → 不算通过**，退回去要证据。

**test-manager 不能做的事**
- **不跑测试，也不改 `code/`** —— 机械上做不到（白名单没有 `test-*`）
- **不替人判"够不够"。** 给证据和判定，收不收口是人决定的
- **不软化 worker 的判定。** 「不通过」「无法执行」照原样汇总

**test-worker 不能做的事**
- **不改 `code/`**（见 §6）
- **不改测试文件去让实现通过。** 那是把裁判变成运动员的另一种形态
- **不写 `doc/交付件/` 的结论。** 报告由 test-manager 汇总

**两者共同**
- **不改验收标准。** 觉得写得不清楚 → 决策记录
- **不写 `doc/决策约束/`**（硬规则 4）。**不把 `status: draft` 改成 `active`。**
- **不跑"验证一下我的修复"** —— 只报问题，不修问题

## 9. 一个反直觉但重要的点

**测试要独立于实现的思路。** 不要先读实现代码再写测试——
先去读**验收标准**，从标准出发设计用例，然后才去看代码。

否则你会不自觉地测"代码做了什么"而不是"要求是什么"，
两者的差集正好是 bug 所在的地方。

这条对 manager 决定测什么同样成立：**先看标准，再看代码。**
