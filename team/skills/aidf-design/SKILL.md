# 设计交付件

## 0. 你产出的东西，下游只能照字面理解

你写完之后你不在场。**N 个角色读同一份文档会有 N 种理解**——这是上下文隔离带来的固有代价。

所以：**散文只写在「理由」节，其余一律写成可求值形式。**

| ❌ 会被各自理解 | ✅ 只有一种读法 |
|---|---|
| "按钮要显眼一点" | "主按钮用 `--color-primary`，高度 40px，同屏只出现一个" |
| "列表加载时给个反馈" | "`state: loading` → 骨架屏 3 行；`state: empty` → 文案「暂无数据」；`state: error` → 文案 + 重试按钮" |
| "移动端适配一下" | "断点 <768px：单列；侧栏折叠为抽屉" |
| "尽量复用现有组件" | "用 `components/Table`；它缺排序能力，排序状态由页面自己持" |

判据：**这句话能不能被求值？** 不能 → 补到能，或者移到「理由」节。

## 1. 交付件结构

走既有的 `doc/交付件/_模板.md`，各节的具体要求：

### 实现结果
页面/组件的结构：有哪些块，谁包含谁。用缩进列表或树，不用散文。

### 接口契约
**你不定接口字段**——那属于 develop-manager 的接口文档。你只写**你需要什么数据**：

```yaml
需要的数据:
  - 订单列表（分页）
  - 每条的：id / 状态 / 金额 / 创建时间
不需要的数据:
  - 用户完整信息（只显示昵称）
```

写"不需要什么"和写"需要什么"同样重要，它防止下游顺手多拉数据。

### 状态枚举
**枚举完，不留"等"。** 每个块的状态必须穷举，每个状态写明渲染什么：

```yaml
块: 订单列表
状态:
  loading:  骨架屏 3 行
  empty:    文案「暂无数据」+ 插图
  error:    文案 + 重试按钮（保留上一次的数据，不清空）
  ready:    分页表格，每页 20 条
  partial:  已加载部分 + 底部 loading 行
```

**漏掉一个状态，实现方就会自己发明一个。** 那是歧义的入口。

### 验证方法
模板的硬要求：必须回答**"人如何独立复现这个东西是对的"**。

"已设计完成"不算。要写成：

```
1. 打开 /orders，DevTools 切成 <768px → 侧栏变抽屉
2. 断网后刷新 → 出现 error 态且保留上一次数据
3. 用 fixture 的 200 条数据 → 分页出现 10 页
```

### 已知限制
**不许留空。** 没有限制就写"暂无已知限制"，但先认真想一遍——
比如"抽屉动画在低端机上会掉帧，未优化"。

## 2. 自检清单

交付前逐条过：

- [ ] 每个状态枚举都穷举了，没有"等"、"之类"、"其他情况"
- [ ] 每个视觉数值都来自决策约束已定的 token，没有新发明的颜色/间距
- [ ] 每个交互都写了失败路径
- [ ] 「验证方法」能被一个不知道上下文的人照着复现
- [ ] 「已知限制」非空
- [ ] 全篇没有"尽量"、"适当"、"合理"这类无法求值的词

## 3. 你不能做的事

- **不改需求。** 需求不合理 → 走「决策记录」：**停下 + 记录，不选择**。
  自己顺手调整需求，是这支团队里最难被发现的一种破坏。
- **不定接口字段。** 那属于 develop-manager 的接口文档。需要接口信息 → 写进决策记录的"我缺什么信息"。
- **不派发、不验收。** 你只出设计交付件；实现由 develop-manager 派 `impl-*` 做。
- **不写 `code/`。** 一个字都不写。你的产物是文档，不是组件。
  想把设计写成组件代码？那说明这个设计还没被想清楚——组件代码会掩盖未定的状态。 

## 4. 边界情况

**需求冻结了但设计发现有缺口** → 这是层3 事件，不是"设计问题"：

- 缺口 `blocks` 了某条验收标准 → 报给 rule-manager 走核心轨
- 不阻塞 → 入非核心队列，你按保守默认先做能做的部分

**不要为了"设计得完整"而自行补需求。** 补上去的部分没有用户原话来源，
会在 rule-manager 的"聚焦核心需求"检查里被标出来。
