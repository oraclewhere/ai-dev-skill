# 需求尽调

## 0. 目标

把决策推进到**层1（可穷举的需求与决策）**，让**层3（不可预见）**变成低频事件。

**不追求"决策全部前置"** —— 那是假的确定感。层3 的存在本身就证明预先穷举不可能。

## 1. 产出物清单

| 产出 | 落到 | 关键约束 |
|---|---|---|
| 尽调文档 | `doc/任务记录/<task>/尽调.md` | 目标 / 非目标 / 开放问题 / 风险 |
| 决策约束草稿 | `doc/决策约束/<id>.md` | **只能到 `status: draft`** |
| 验收标准 | 各任务记录的「验收标准」节 | 人写或人批准 |
| 不可逆动作清单 | 决策约束的一节 | 见 §3 |
| 总授权 | 决策约束的一节 | 见 §4 |
| 三档疑问清单 | 离开声明时产出 | 见 §6 |

## 2. 提问的形态：结构化，且必带保守默认

```
question: "订单超时后是自动取消还是保留待支付？"
why_it_matters: "影响 task-0003 的状态机设计，也影响验收标准 2"
options:
  - "自动取消（代价：用户回来看不到订单）"
  - "保留待支付（代价：需要清理任务）"
default_if_unanswered: "保留待支付"
```

**没有 `default_if_unanswered` 的问题不许提。** 否则就是把决定责任推回给人。

**提问走主会话**：subagent 没有 `AskUserQuestion`。
把清单交回主会话转达，然后**继续做可前置的部分**，不要停在那里等。

## 3. 不可逆动作清单

真正不可逆的工程动作很少，**可以穷举**：

- 删数据
- 对外发布（发版、发消息、写外部系统）
- `git push`
- 动凭证 / 密钥
- 调用有外部副作用的接口（支付、通知、第三方写操作）

**判据是"在不在清单里"，不是"这次改动大不大"。** 写法：

```yaml
不可逆动作:
  - id: irr-001
    action: "调用真实支付网关"
    detect: "import 自 pay/gateway 且非 mock 模式"
  - id: irr-002
    action: "删除 order 表数据"
    detect: "出现 DELETE FROM order / drop 相关语句"
```

每条带 `detect`，让它可机械识别。撞上清单 → **保守默认不做**，入队等人。

## 4. 总授权：问题类型 × 路径范围

授权到**问题类型**。所以类型的成员资格必须是**客观事实**，每个类型带检测信号：

- ❌ 「实现细节问题」——没有边界，什么都能塞
- ✅ 「第三方依赖版本冲突」——manifest 冲突或报错命中固定模式
- ✅ 「同一验收标准下两个模块的接口字段命名不一致」

```yaml
授权:
  - type: "第三方依赖版本冲突"
    detect: "lockfile 冲突 / 依赖解析报错命中固定模式"
    paths: [code/order/, code/pay/]
    scope: "可自行裁决版本选择，不得引入新依赖"
```

**副作用（是好的）**：类型就是判据集的分组名。
人写的总授权（按类型）与复盘长出的判据（按类型）自然合成一个结构。
"某类型下推翻记录累积太多"本身就是信号——授权给早了，或该拆。

## 5. 验收标准

**必须在执行前存在，由人写或人批准。** 团队模式下时间点前移：尽调阶段一次性写完全部任务的。

写法要求：**可求值**。下游读它时你不在场。

| ❌ | ✅ |
|---|---|
| "性能要好" | "1000 条订单列表接口 P95 < 300ms" |
| "支持并发" | "10 并发下单不出现超卖（库存余量与实际扣减一致）" |
| "错误处理好" | "网关超时 → 返回 504 且订单保持待支付；重试 3 次后进入人工队列" |

## 6. 离开声明

人在离开前主动声明。**它不是新机制，是队列的批量预填充**——把待裁项在离开那一刻往后推演一遍。

### 6.1 三档，判据还是 `blocks`

| 档 | 判据 | 归属 |
|---|---|---|
| **当前需要** | 现在就被阻塞（`blocks` 非空且已到那一步） | 核心轨，**人现在定** |
| **预期** | 将来会阻塞（`blocks` 可预填，还没到） | 人可现在定，或授权给 rule-manager |
| **不确定** | 不知道会不会阻塞 | 非核心轨，入队 |

### 6.2 每条必带两样，否则不许进清单

不设这条约束，agent 就有动机把所有事都列成"不确定"——将来做错了可以说"我列过了，你没定"。
**那是责任转移。**

1. **保守默认** —— 没人定的话我打算怎么做
2. **事实锚点** —— 这条疑问基于哪个**已存在**的产物（文件 / 交付件 / 验收标准）

第 2 条把"根据当前的进展"落成了机制：**疑问必须锚定到已产出的东西，不能基于想象提问。**

### 6.3 人只处理"当前需要"档

**这条是防退化的关键。** 如果人必须答完每一条才能走，离开声明就变成了"答完题才准走"，
反而把人锁住——正是要消除的东西。

**人有权说"剩下的全走默认"，一句话结束。**

### 6.4 "预期"档产出临时授权

人选"这个留到那时候让 rule-manager 裁" → 产生**针对具体问题的授权**，
比尽调期的类型级授权精准得多，正好填上"类型级授权"与"具体裁决"之间的空档。

同类预期反复出现 → 可固化成类型级授权（与判据生长同源，自底向上）。

### 6.5 自行检验：这个数字高说明你没做够

> **离开声明"当前需要"档的条数 / 任务数**

它的价值在**测出来的时机**：此时错误还便宜（大不了人现在定一下），
而不是等人回来发现已经返工了。

### 6.6 触发与否都留痕

触发了记清单与裁定；**没触发记一条"本次离线无声明"**。轻量，
但让这个选择可见、可统计——否则"永远不触发"会导致"回来被队列困住"毫无预警。

## 7. 一处诚实说明

**"预期"档含判断成分**，因为预测"将来会阻塞"本身就是判断。消不掉，用两个方式限制影响面：

- 必须附客观依据（哪条验收标准可能受影响），无依据的降到"不确定"档
- **它只是建议，不是判据** —— 人可以全盘不理，直接留到那时候裁决

最坏情况是白列几条，不造成系统性影响。

## 8. 聚焦核心需求（rule-manager 会查这条）

```yaml
来源: "用户原话：'我希望下单后能随时看到进度'"
```

找不到来源的条目 → 删掉，或显式标记 `AI 建议，待批准`。
**聚焦由"有没有原话来源"决定，不由"感觉相不相关"决定。**
