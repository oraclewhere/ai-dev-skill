# 实现阶段

**一份规则，两个使用者**：develop-manager 编排，impl-worker 执行。
写在同一个文件里是刻意的——分支命名、提交规则这些约定两边都要遵守，
放在两处就会各自漂移。

## 0. 开工前的就绪检查（不满足就不开工）

```
[ ] 任务记录存在：doc/任务记录/task-NNNN.md
[ ] 「验收标准」非空，且由人写或人批准
[ ] 决策约束 status: active（不是 draft）
[ ] 需要设计的任务：设计交付件已就绪
[ ] （manager）接口文档已冻结
```

**任何一条不满足 → 不要开始。** 按 §7 的出口处理，不要"先做起来再说"。

理由：原流程的第一步是"先分类再动手"，由模型判定这是管理类还是执行类。
团队模式下这个动作**已外移**——你收到的输入必须已被上游判定完毕。
自己补判，等于把"我该不该被监管"的判断权拿回被监管者手里。

## 1. 接口文档（develop-manager 的产物，派发前必须冻结）

`doc/交付件/<task-NNNN>-接口.md`，照 `doc/交付件/_接口模板.md` 写（安装时一并放好）。

**它是本次派发的全部依据**，所以要写成**结论式、可求值式**：

| ❌ | ✅ |
|---|---|
| "订单模块要和库存服务交互" | "`POST /inventory/reserve`，请求 `{sku, qty}`，返回 `{reserved_id}`；失败码 `409 OUT_OF_STOCK`" |
| "错误处理要友好" | "`qty <= 0` → `400 INVALID_QTY`；`sku` 不存在 → `404 SKU_NOT_FOUND`" |
| "数据结构大致是……" | 附完整类型定义（可复制粘贴的那一份） |

**为什么这条是硬的**：同一份文档要发给 N 个 worker，而它们各自读出的意思不会完全一样
——隔离把"漂移"换成了"歧义"。文档越是结论式，N 个读法越收敛到同一个。
散文只允许出现在「理由」一节，那节不参与对接。

**没冻结 → 不要派发。** 边写边派的结果是每个 worker 拿着一份不同版本的契约，
而它们互相看不见对方的上下文，冲突要到对接时才暴露。

## 2. 配技能（查表，不挑）

按 `aidf-equip` §6 的任务级映射表，为每个 worker 查出技能。
**匹配不上就写"无匹配"，如实报**，不许挑一个看起来像的。

## 3. 派发（develop-manager）

一个 worker 一份**窄**任务。prompt 里必须写齐：

- **接口文档的路径**（写路径，不要抄内容——抄了就多一份会漂移的副本）
- **它负责的那一部分**，窄到能独立闭环
- **它不能碰的部分**，以及为什么
- **本次配给它的技能名**
- **产物写到哪**

并行派发互相独立的部分（一条消息发多个 Agent 调用）。有依赖的必须串行。

**必须记住的中继事实**：派发是**有损中继**——主会话看不到 worker 的 transcript，
只能看到 manager 的转述。所以**凡是要验收的东西，worker 必须落盘成文件**，
manager 按文件校验，不接受"它说它做完了"。

## 4. 建任务记录

`doc/任务记录/task-NNNN.md`，用既有模板。**注意分工**：

| 节 | 谁填 |
|---|---|
| 目标 | develop-manager（从需求文档的对应条目来） |
| 验收标准 | **人**。AI 不填、不改 |
| 上下文预算 | develop-manager |
| 交接说明 | 多数任务不需要，见 §8 |
| 决策记录 | 触发出口时填 |

### 上下文预算怎么写

工作量单位是**"能否在一个 session 内闭环"**，不是人天。

```yaml
context_budget:
  files: 12          # 预计要读/改的文件数
  est_tokens: 80000  # 诚实估
  handoff_at: "读代码阶段结束时"
```

**估不准就写"不确定"并说明**，别写个好看的数字。
超出预算 → **拆任务**，不要硬撑。硬撑的结果是上下文漂移，而漂移的产物你自己察觉不到。

## 5. 建分支与提交（impl-worker）

**分支名必须带 `task-NNNN`。一个分支一个任务。**

```bash
git checkout -b task-0003-order-status-machine
```

- 硬校验：分支名含 `task-NNNN` 且该任务记录真实存在（伪引用会被拦）。
- **一个分支一个任务**：跨任务的分支会让"这个分支实现了什么需求"不可判定。
  需要跨任务 → 说明任务粒度超了 → 回到 §4 拆任务。

分支描述取自任务记录的「目标」节——所以「目标」要写清楚，它会被复用。

**写码与提交**：

- **只在 `code/` 下写。** `scripts/` 等目录按**路径**豁免，不受硬规则管。
  豁免由目录决定，不由"这算不算脚本"的判断决定。
- commit message 必须含 `task-NNNN`。hook 查两件事：**ID 存在性 + 任务记录真实存在**。
  写一个不存在的 ID 通过校验不叫遵守规范，叫绕过校验——会被专门拦。

```bash
git add code/order/
git commit -m "feat: 订单状态机 — task-0003"
```

**`code/` 的写权限是白名单**：只有 `impl-*` 卡能写（主会话不受限）。
develop-manager、test-* 写了都会被拦——这不是建议，是机械事实。

## 6. 对接（develop-manager）

- 逐个 worker 的产物**对照接口文档**：签名、字段名、错误码、返回结构，逐条核。
- **实际跑一次**把各部分接起来。跑不通 → 归因：接口文档没写清（改文档，你改）
  还是 worker 写错了（退回原 worker，带具体证据）。**两者归因不同，处理方式也不同。**
- 产出交付件：`doc/交付件/<id>.md`，走既有模板。两个节要特别较真：
  - **「验证方法」**：必须回答**"人如何独立复现这个东西是对的"**。
    "已测试通过"不算——那是 test-manager 的结论，不是复现方法。
  - **「已知限制」**：**不许留空。**

## 7. 唯一异常出口：「决策记录」

遇到任何**需要判断**的事，走这里：**停下 + 记录，不选择。**

什么算"需要判断"：需求有歧义、**接口文档定不下来**、两个 worker 的实现冲突、
要引入新依赖、要改一个不属于本任务的模块、验收标准本身有问题。

```yaml
停在哪: "task-0003 的接口文档要求库存同步扣减，但决策约束 d-0002 要求异步化"
需要谁定: "rule-manager / 人"
我缺什么: "两条哪个优先"
我的保守默认: "接口文档里把扣减调用抽成独立函数，先按同步实现并标记 TODO(task-0003)"
```

**保守默认必须写，且必须是"可逆的、不阻塞其他推进的"那一个。**

**不要自己权衡后悄悄选一个。** 那个降级不可观测，是这套方法论最不能接受的失败。
写下来就变成可见的、可复盘的、下次可固化成判据的——**这就是出口存在的全部理由。**

## 8. 交接说明在团队模式下多数用不上

原来那套（`context_budget` / `handoff_at` / 交接说明）是为"单个 session 干到漂移"设计的。
团队模式下**每次角色调用都是全新上下文**，所以多数任务不需要交接说明。

还需要它的两类：
1. 任务确实大到一个 session 装不下，且被停下来；
2. 人自己在项目里直接干活。

**但"文档先行"没有被取消**——它只是从"离职前整理"变成了"正常工作的形式"。
产物（任务记录、接口文档、交付件）本来就是文档。

## 9. 两个角色各自不能做的事

**develop-manager**
- **不写 `code/`** —— 机械上做不到（白名单只有 `impl-*`）。
- **不为了跑通而改接口文档去迁就实现。** 实现对了就走出口说明文档为什么错；
  实现错了就退回去改实现。
- **不接受"worker 说它做完了"作为验收。** 只认落盘的产物。

**impl-worker**
- **不改接口文档。** 那是所有 worker 的共同输入。
- **不碰不属于自己边界的部分。** 需要 → 走 §7。
- **不为了跑通而放宽实现**（例：因为测试数据缺字段而注释掉校验）。
- **不改测试文件去适配自己的实现。**

**两者共同**
- **不写 `doc/决策约束/`**（硬规则 4，人维护、AI 只读）。hook 会拦。
- **不改「验收标准」。**
- **不把 `status: draft` 改成 `active`。**
- **不碰测试结论。** test-manager 的判定不改；有问题走 §7，不是去改测试。
