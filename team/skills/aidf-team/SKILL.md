# 流程状态机

## 0. 一句话

人的在场窗口是**尽调期**。尽调完，人走，团队自己跑；人回来时批量收口。

控制权靠四个点保住，不靠人在场：**规则由人定 / 结果由人审 / 异常由人裁 / 合入由人触**。

## 1. 七个阶段

```
⓪ 装配     人经结构化选项定**角色级**技能 → 派 subagent 装 → 装配后自检（查表）
            ↓ 不装配也能跑，但风险要当面给（aidf-equip §2）
① 尽调     需求分析师产出尽调文档、决策约束草稿(draft)、验收标准、不可逆清单、总授权
            **技术栈也在这一步定下来** —— 它是任务级技能的唯一依据
             ↓ 分析师发起审核（不是"觉得够了"）
② 审核 loop 各角色读文档产出 blocking_questions，只对 diff 提意见
            rule-manager 监督：每条需求必须有「来源: 用户原话」
             ↓ 终止条件（见 §3，客观清单）
③ 冻结     人确认 → 决策约束 draft → active
             ↓
④ 开发     designer → develop-manager（接口文档 → 派 impl-* → 对接）→ test-manager（派 test-*）
            层3：blocks 非空 → rule-manager 裁决 / blocks 空 → 入队
             ↓
⑤ 人回来   离开前：离开声明（见 aidf-intake）
            回来后：秘书渲染队列 → 人批量裁定 → 推翻率记录
             ↓
⑥ 收口     合入发布分支（唯一由人触发的动作）
```

**⓪ 和 ① 的顺序不能颠倒。** 角色级技能依赖"要做什么样的项目"，尽调依赖人的在场——
把装配放前面是因为它也要问人，两次提问合并成一次在场。

## 2. 两层结构：六个角色 + 两层工人

```
主会话（团队声明卡）
  ├─ requirements-analyst    尽调
  ├─ rule-manager            取证裁决与监护
  ├─ designer                设计交付件
  ├─ develop-manager ──派──> impl-worker / impl-<域>   （唯一能写 code/ 的层）
  ├─ test-manager    ──派──> test-worker / test-<类>   （只能写 tests/）
  └─ secretary               队列与人机议程
```

**主会话够不着工人层。** 团队声明卡的 `tools` 里是
`Agent(requirements-analyst, rule-manager, designer, develop-manager, test-manager, secretary)`
——一份白名单，名单里没有 `impl-*` / `test-*` / `general-purpose`。
所以实现与测试的派发**只能**经过各自的 manager。这是结构，不是约定。

它换来两件事：
1. "谁负责对接""谁负责汇总"不会在派发链上丢失——有一个具名角色在管它。
2. `code/` 的写权限能做成**白名单**（只有 `impl-*`），因为写码的人必然出自 manager 这一层，
   名字由 manager 定，前缀可控。黑名单做不到这点：工人名字是动态的，永远列不全。

## 3. spawn 规范

**把该读的文档路径写进 prompt，不要把文档内容抄进 prompt。**
抄一遍就多一份会漂移的副本——这正是"隔离把漂移换成歧义"的放大器。

```
Agent(
  subagent_type: "requirements-analyst",
  prompt: "读 doc/任务记录/task-0007/尽调.md 与 doc/决策约束/d-0003.md（当前版本），
           产出本轮 blocking_questions。上一轮的意见在 审核-r2.md，只看 diff。"
)
```

**只传 diff。** 每轮把需求全文重述一遍，成本是平方级增长，且每轮都有重述带来的漂移。

并行 spawn 互相独立的角色（用一条消息发多个 Agent 调用）。
有依赖的必须串行——designer 要等冻结，develop-manager 要等设计稿，test-manager 要等交付件。

### 3.1 派发链是有损中继（派发的人必须记住）

主会话看不到 worker 的 transcript，只能看到 manager 的转述；
manager 也看不到别的 manager 的工人。**隔一层就少一层事实。**

所以有一条贯穿全程的规则：

> **凡是要被验收的东西，必须落盘成文件。**

manager 按文件校验，不接受"它说它做完了"；主会话按文件验收 manager。
证据形态也一样——**能被人重跑一遍的命令加输出**才算证据（`aidf-verify` §2）。

### 3.2 技能怎么交给工人

| 场景 | 写在哪 |
|---|---|
| 每类工人的技能长期固定（例：所有 `impl-backend` 都配 python） | 那张卡自己的 `skills:` frontmatter |
| 每次派发不同（例：这次要 react，下次要 vue） | 派发的 prompt 里点名 |

两种都要**先查装配表**：`effective: false` 的技能当作**没有**（`aidf-equip` §4）。

## 4. 终止条件：客观清单，逐条查

**"分析师觉得可以了"不能作为终止条件。** 它能做的只是**触发**一轮审核。

冻结前的判定，逐条机械核对（`aidf-intake` 里有对应的检查脚本思路）：

| # | 条件 | 怎么查 |
|---|---|---|
| 1 | 每条需求都有 `来源:` 字段且非空 | grep 文档 |
| 2 | 每个被审角色的 `blocking_questions` 为空 | 读回执文件 |
| 3 | 每个被审角色的 sign-off 字段非空 | 读回执文件 |
| 4 | 悬空问题只有两个去处：`resolved`（附答案来源）/ `accepted_risk`（附 rule-manager 接受记录） | grep 状态字段 |
| 5 | 决策约束含：不可逆动作清单、总授权（类型 + 路径） | 读文档 |
| 6 | 每个任务的「验收标准」非空且由人写或人批准 | 读任务记录 |

**有任何一条不满足 → 不冻结。** 不许"先跑起来再说"——冻结是硬规则 4 的机械检查点。

## 5. 人的四个控制点，分别落在哪

| 控制点 | 落在哪个时刻 | 产出 |
|---|---|---|
| 规则由人定 | 尽调期一次 | 决策约束（总授权 / 不可逆清单 / 验收标准） |
| 结果由人审 | 交付件 + 全新上下文 subagent 审计 | 复盘报告 |
| 异常由人裁 | 人回来时 | 队列裁定 |
| 合入由人触 | 收口 | merge 到发布分支 |

**尽调期的确认是免费的**——人在回答需求分析师的提问，本来就在场。
同理，⓪ 装配的技能选择也并进这次在场，不要另外发起一轮问答。

## 6. 成本与预算

工作量单位是**"能否在一个 session 内闭环"**，不是人天。

- 单个任务超出上下文预算 → 拆任务，别硬撑。
- 单轮尽调循环超预算 → 拆需求，别硬撑。
- 硬撑的结果是上下文漂移，**而漂移的产物当事方察觉不到**。

**装配本身也吃预算**：技能正文会留在对话里，压缩后每个技能只重挂最近 5000 tokens，
共享 25000 tokens 的额度——**装太多，前面的会被挤掉，等于没装**。
所以 §1 的"只装角色级"不只是为了不猜技术栈，也是为了不把额度烧在本次用不到的东西上（`aidf-equip` §7）。

## 7. 人的回访信号

**队列长度**是客观信号：`doc/待批/` 里 `status: open` 的条数。
积压到阈值 → 提示"该回来看一眼了"。

这是**纯观测提示，不阻塞任何东西**。它不是门槛——
任何"改动大到就停"的门槛本身是判断，且会把人重新锁回机器上。

**返工成本的上界 = 回访间隔。** 频繁回来 = 单次沉没小但打扰多；少回来 = 打扰少但单次沉没大。
这是人自己的旋钮。

## 8. 团队做不到什么（要在需要时如实告诉人）

- 层3 事件不能前置，只能压低频率
- 没有"停下等人"的门槛，返工变成沉没工作量
- rule-manager 的判断没被消除，只被约束成可审计的取证
- **hook 会 fail open**，拦截失效时不会自己喊；判据是记录文件，不是"没被拦就是对"
- **插件类技能装完当会话用不了**，得人敲一次 `/reload-plugins`（`aidf-equip` §3）
- 最终验收与合入仍由人做

## 9. 相关

- 技能装配（角色级 / 任务级、双通道、自检） → `aidf-equip`
- 尽调与离开声明 → `aidf-intake`
- 取证裁决与监护 → `aidf-adjudicate`
- 队列与裁定 → `aidf-queue`
- 设计 → `aidf-design`
- 实现阶段（develop-manager + impl-worker） → `aidf-deliver`
- 验证阶段（test-manager + test-worker） → `aidf-verify`
